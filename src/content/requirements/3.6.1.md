## Requirement

"Establish an operational incident-handling capability for organizational systems that includes preparation, detection, analysis, containment, recovery, and user response activities."

## Objectives

[a] an operational incident-handling capability is established;
[b] the operational incident-handling capability includes preparation;
[c] the operational incident-handling capability includes detection;
[d] the operational incident-handling capability includes analysis;
[e] the operational incident-handling capability includes containment;
[f] the operational incident-handling capability includes recovery; and
[g] the operational incident-handling capability includes user response activities.

## Sufficient

- **Endpoint detection and response tooling paired with a written policy and procedure set, without a staffed security operations center or around-the-clock monitoring.** Assessors have accepted this combination as reaching the capability objective; continuous staffed monitoring is a stronger option, not a floor. [a][c]
- **A capability that reaches beyond network intrusions to cover physical loss or theft of equipment holding CUI.** Practitioner consensus treats theft of a CUI-bearing device as within this requirement's scope, not something a separate physical-security program alone addresses. [e][g]
- **Two coordinated response documents, one for physical loss or theft aligned to facility-clearance rules and one for cyber events aligned to the 800-171 objectives, with some functional overlap between them.** Assessors have accepted this split where an organization already tracks physical incidents under a separate compliance regime. [a]
- **Role-based user response duties: recognizing and reporting a suspected incident, following the documented procedure, supporting the investigation, and carrying out assigned remediation steps.** This is how the user response objective gets satisfied at the individual level rather than only at the program level. [g]

## Insufficient

- **A capability that can point to only one or two of preparation, detection, analysis, containment, recovery, and user response, treating the rest as implicitly covered.** Assessment Guide discussion expects each element to be addressed on its own terms; an assessor scoring against the individual objective letters will not credit an element that is never actually described. [a-g]
- **An incident-handling policy with no defined intake channel, no contact list, and no way to track an incident from creation to closure.** Assessment Guide example content ties objective [a] and [b] to exactly these mechanics; a policy that skips them reads as aspirational rather than operational.

## Over-engineering

- **Standing up continuous staffed monitoring or dedicated around-the-clock coverage solely to satisfy the detection element.** Endpoint tooling that generates and retains alerts, tied to a documented response procedure, reaches the same objective at a fraction of the cost. [c]
- **Building a single incident-handling document that tries to anticipate every scenario in exhaustive detail before it is ever used.** A shorter procedure that names roles, an intake path, and the six required elements, refined after each test or real event, satisfies the objectives without the up-front cost of a document nobody will keep current. [a][b]

## Edge cases

- **Keeping an externally contracted incident response provider out of assessment scope.** One accepted approach treats a single provider staff member as functionally an organization employee, using organization-owned credentials, devices, and management consoles, with the provider engaged only for incidents affecting CUI-processing devices; for a very small CUI footprint, a documented policy of rebuilding a compromised device rather than scoping the provider in has also been accepted. Both are situational to small environments, not a general rule.
- **A 2024 change to the DFARS cyber incident reporting requirement removed a prior certificate condition tied to reporting, but the regulatory text referencing it was not immediately conformed everywhere.** Practitioners have continued renewing the older certificate type as a precaution while this gap gets sorted out; no settled resolution exists yet.
- **Assessment Guide worked examples lean toward cyber scenarios more than physical ones.** Practitioner consensus warns against treating those examples as an exhaustive checklist; satisfying only what an example describes does not guarantee every applicable objective is met, particularly for the physical-theft scenario.

## Evidence examples

- **Incident-handling policy naming each of preparation, detection, analysis, containment, recovery, and user response as a distinct activity.** [a-g]
- **A dedicated incident intake channel (a mailbox or phone number) and an escalation contact list.** [b]
- **Incident tracking log or ticketing record showing an entry from creation through closure.** [a][d]
- **DFARS 252.204-7012 reporting elements incorporated into the plan, including the 72-hour reporting window and the 90-day media retention requirement.** [f]
- **Reference to published incident-handling guidance used as the basis for the internal procedure.** [b][c][d]

## Related requirements

- **3.6.2** depends on the tracking and documentation this capability produces; without an operational capability there is nothing to report.
- **3.6.3** tests the capability this requirement establishes; a plan that has never been exercised cannot demonstrate these objectives are functioning in practice.
- **3.3.1** and malicious code protection requirements feed the detection element [c] with the logging and alerting this requirement's capability relies on.
