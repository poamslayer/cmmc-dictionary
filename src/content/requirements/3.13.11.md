## Requirement

"Employ FIPS-validated cryptography when used to protect the confidentiality of CUI."

## Objectives

[a] FIPS-validated cryptography is employed to protect the confidentiality of CUI.

## Sufficient

- **FIPS-validated cryptography relied on specifically at the point where CUI actually leaves a physically protected environment**, such as in transit outside the boundary or at rest on a portable device, rather than expected everywhere cryptography merely happens to run. [a]
- **Physical safeguards, such as a locked facility with controlled access, accepted as the confidentiality protection for CUI that never leaves that protected space under Rev 2**, without requiring FIPS-validated encryption for that same information inside the boundary. [a]
- **An application that hands its encryption operations to an already FIPS-validated operating-system cryptographic module**, so the application inherits that module's validation rather than needing a separately validated module of its own. [a]
- **Connections into a government-authorized cloud tenant**, since FIPS-validated cryptography is a baseline element of that authorization and covers the session for the tenant's covered functionality. [a]
- **A cryptographic module whose validation certificate has moved to historical status, logged as a temporary deficiency rather than treated as an automatic failure**, when the underlying software is otherwise in active, documented use. [a]
- **Network equipment that only passes encrypted traffic through without performing the encryption itself does not need its own FIPS validation**, since the objective attaches to the point where cryptography is actually used to protect confidentiality, not to every device the traffic happens to cross. [a]

## Insufficient

- **A vendor description of a product as "FIPS compliant" rather than FIPS validated.** Compliance is a marketing description, not the tested and certified status the objective requires; point to the specific validation certificate for the module in use. [a]
- **Using a well-known, sound encryption algorithm inside a software module that does not itself appear on the validated module list.** The algorithm being approved is not the same as the implementing module being validated. [a]
- **Relying on a document-handling application whose cryptographic modules are listed only as historical, as the primary means of encrypting CUI, without verifying the modules remain adequate or logging the gap.** [a]
- **A tunnel that provides encryption but not FIPS-validated encryption where FIPS-validated protection is required.** This is a scored deduction, not merely a documentation gap, and is one of the very few objectives above the one-point level eligible for a plan of action rather than requiring full implementation at assessment. [a]
- **Assuming every browser inherits the operating system's FIPS-mode cryptographic module for its TLS connections.** Some browsers bundle their own cryptographic library instead, so operating-system FIPS mode alone does not verify that browser's traffic is protected. [a]

## Over-engineering

- **Requiring FIPS-validated cryptography on network switches or other pass-through devices that never perform encryption themselves.** The objective attaches to where cryptography is used to protect confidentiality, not to every device traffic happens to cross. [a]
- **Encrypting traffic to a device, such as a printer, that sits entirely inside a physically protected boundary**, when physical safeguards already satisfy the objective for that path under Rev 2. [a]
- **Encrypting a second time inside a tunnel that only re-wraps data already protected by validated encryption at a lower layer.** The objective is satisfied once, at the point protection is actually needed. [a]
- **Applying FIPS-validation requirements by default to wireless access points, remote-access tooling, multi-factor devices, and every other component**, rather than scoping FIPS specifically to where CUI confidentiality depends on encryption. [a]
- **Purchasing FIPS-validated network hardware before confirming that device is actually a point where CUI confidentiality depends on its encryption function.** [a]

## Edge cases

- **Wireless transmission of CUI.** Consumer-grade access points rarely carry FIPS validation. One documented workaround is to apply FIPS-validated encryption before data reaches the wireless layer, or to require a wired connection for CUI traffic instead of searching for a validated access point. [a]
- **Printing CUI.** Producing a FIPS-encrypted print job end to end is difficult with most consumer printing paths; a dedicated, physically controlled print device reachable only from the machine that prints to it is a documented workaround, not a settled universal answer. [a]
- **A device that must leave the physically protected boundary, such as a laptop taken offsite.** Once outside that boundary, physical safeguards no longer apply, and confidentiality protection has to come from FIPS-validated encryption for both storage and transmission. [a]
- **Whether alternative physical safeguards remain available at all is itself a Rev 2 versus Rev 3 question.** The next revision is expected to remove that alternative, meaning equipment purchased today to rely on physical protection alone may need FIPS-validated encryption added later. This is a direction to plan around, not the current Rev 2 standard this file describes.
- **Running an operating system version newer than the specific version carrying an active FIPS validation certificate is extremely common in practice**, and is treated as a routine, loggable temporary deficiency rather than a reason to avoid patching. [a]
- **Whether a specific FIPS security level, as opposed to validation itself, is required.** No specific level is mandated unless contract language calls one out, so the baseline expectation is validation at some level rather than a named level. [a]
- **Scoring and POA&M treatment.** A gap where encryption is implemented but not FIPS-validated is deducted at the three-point level under 32 CFR 170.24(c)(2); a gap where encryption is not implemented at all is deducted at the five-point level. This requirement's three-point state is the only requirement above one point that 32 CFR 170.21 permits on a plan of action; the five-point state is not POA&M eligible.

## Evidence examples

- **The specific cryptographic module validation certificate number for each point where encryption protects CUI confidentiality.** [a]
- **Operating system FIPS-mode configuration setting, including its mobile-device-management equivalent for managed devices.** [a]
- **A scan or configuration export showing FIPS-mode enforcement across managed devices.** [a]
- **Disk-encryption status output showing a FIPS-compliant cipher suite in use.** [a]
- **A written mapping of where in the CUI data flow encryption is applied, tied to system diagrams and asset inventory, with the applicable module identified at each point.** [a]

## Related requirements

- **3.13.8** (data in transit) is the requirement that triggers when cryptography is needed at all; this requirement supplies the FIPS-validation standard that cryptography must meet once 3.13.8 applies.
- **3.8.6** (media encryption) and **3.1.19** (mobile device encryption) both depend on this requirement for the same reason: encrypting a portable device or removable media is only compliant if the encryption used is FIPS-validated.
- **3.13.10** (key management) covers the keys behind the cryptography this requirement validates; a well-managed key is a separate objective from a validated module.
