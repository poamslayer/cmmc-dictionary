## Requirement

"Provide a system capability that compares and synchronizes internal system clocks with an authoritative source to generate time stamps for audit records."

## Objectives

[a] internal system clocks are used to generate time stamps for audit records;
[b] an authoritative source with which to compare and synchronize internal system clocks is specified; and
[c] internal system clocks used to generate time stamps for audit records are compared to and synchronized with the specified authoritative time source.

## Sufficient

- **Standard network time protocol synchronization pointed at a single specified source.** Practitioner consensus treats this as the default, unremarkable implementation for most environments. [b][c]
- **Cloud-hosted, SaaS-only environments where the platform (for example Microsoft 365) already synchronizes clocks for the logs it generates.** No added configuration is typically expected when the organization does not operate its own servers. [b][c]
- **Evidence that timestamps across separate systems, such as a domain and separate network gear, line up with one another after synchronization.** Assessors have accepted a side-by-side comparison as proof the sources agree, though this stays a soft spot; see Edge cases. [c]
- **A documented, defined authoritative source named in policy or configuration**, rather than left implicit. The Assessment Guide discussion frames this as identifying a source organizations can point to and defend. [b]

## Insufficient

- **Pointing different classes of equipment at unrelated public time services with no proof they agree with each other.** The objective language specifies "an authoritative source," singular, and assessors reading that literally expect one specified source, or a demonstrated agreement between sources if more than one is used. [b]
- **Relying on third-party or vendor-hosted time services without any means to verify those services stay in sync with one another.** An unverifiable claim of alignment does not substitute for a comparison an assessor can inspect. [b][c]
- **Treating assessor leniency as the plan.** Assuming an assessor will simply be reasonable about an unresolved gap, instead of documenting a defensible answer, is called out in practitioner consensus as a real assessment risk rather than a safe default. [b][c]

## Over-engineering

No documented position beyond the Assessment Guide; see confidence.

## Edge cases

- **Network appliances that hard-code their own time service and give the organization no way to point them elsewhere.** A documented workaround, such as handing other devices the same servers the appliance already uses through a DHCP option, is discussed as a practical approach; no single resolution is settled, so the outcome depends on the assessor.
- **Time servers embedded in a cloud service provider's platform or in a virtual desktop environment, which the organization cannot reconfigure.** Practitioner consensus expects assessors to be reasonable here given a written justification, but this reasonableness is itself flagged as a risk area rather than a guarantee.
- **Third-party authentication or multi-factor tooling that stamps events using its own clock or time zone**, creating a possible mismatch with the organization's chosen source. No resolution is documented; treat it as an open item to confirm rather than assume compliance.
- **Whether the Assessment Guide's Examples and Potential Assessment Considerations carry the same weight as the Discussion text.** One position treats DoD-added Examples and Considerations as authoritative because they sit inside the Assessment Guide; another position treats them with more skepticism because they were not drafted by NIST. The outcome depends on the assessor.
- **Rev 3 direction (mentioned in source discussion, not restated here).** Practitioner discussion notes a coming shift toward a timestamp precision and format requirement rather than a named-source requirement; this is a direction to watch, not the current Rev 2 standard this file describes.

## Evidence examples

- **Configuration screenshot or export showing which specified time source a system synchronizes against.** [b]
- **A side-by-side comparison of timestamps from two or more systems demonstrating agreement after synchronization.** [c]
- **DHCP scope configuration passing time server addresses to devices that cannot be pointed at a source directly.** [b][c]
- **Audit log excerpts showing timestamps recorded in a consistent, defined format.** [a]

## Related requirements

- **3.3.1** depends on this requirement: audit records are only as useful as the timestamps this capability generates, since event review across systems requires a shared, trustworthy clock.
- **3.3.2** correlates user actions to specific events, which also depends on timestamps that agree across the systems being reviewed.
- **3.3.8** protects the audit records and logging tools whose timestamps this requirement establishes, so a compromised time source undermines the protection the later requirement provides.
