## Requirement

"Establish and enforce security configuration settings for information technology products employed in organizational systems."

## Objectives

[a] security configuration settings for information technology products employed in the system are established and included in the baseline configuration; and
[b] security configuration settings for information technology products employed in the system are enforced.

## Sufficient

- **A published hardening checklist (a security technical implementation guide or equivalent benchmark) completed against each asset type, with every deviation written down along with the reason for it.** This is accepted as both the baseline and its enforcement record in one artifact, and using a published checklist reduces how much original documentation an organization has to produce. [a][b]
- **A modern device-management platform (conditional access, compliance policies, update rings, a settings catalog) used to enforce settings, paired with a separate written document stating what those settings are supposed to be.** A console's current state is not itself the baseline; the accepted pattern writes the intended settings down separately so there is something to compare the live configuration against. A golden image is one way to do this, not the only way. [a][b]
- **Group policy enforcement paired with a documented change-management process for any deviation.** [a][b]
- **A separate software-specific baseline (for a browser or a document reader, for example) incorporated by reference into the operating-system baseline, so a software update does not force a rewrite of the whole OS baseline.** [a]
- **For software that updates itself frequently, documenting the configuration setting as "automatic updates enabled, with a policy against disabling or blocking them" rather than tracking individual version numbers.** [a][b]
- **A firewall rule export in spreadsheet form with a business justification column and a ticket reference in each rule comment, so approval history can be retrieved later.** Assessors have accepted this format, and it can double as evidence for the nonessential-ports-and-services requirement too. [a][b]
- **A written statement that testing a hardening setting carries too much operational risk, used as the rationale for not testing it.** [b]

## Insufficient

- **A raw configuration file offered as the whole baseline, with no accompanying explanation of why any given setting was chosen or whether it is security-relevant.** A config file alone does not show which settings are subject to change approval, and does not map to the requirements it is meant to satisfy; assessors expect that mapping written down somewhere. [a]
- **A backup of the current configuration presented as if it were the definition of what the configuration should be.** Capturing the current state is not the same as establishing the intended state; the objective asks for an established setting to enforce against, not a snapshot of whatever happens to be running. [a]
- **Configuration settings that are not tied back to the specific requirements they are meant to satisfy.** A strong pass requires that mapping to exist somewhere, even informally. [a]
- **Firewall or similar rules with no comment or reference explaining why the rule exists.** Practitioner consensus is that undocumented rules become unexplainable within a couple of years, which is treated as a documentation failure at assessment. [b]

## Over-engineering

- **Writing an individual configuration baseline for every application bundled with the operating system, such as a basic text editor or a basic image viewer.** The operating system's general security settings already govern software of that kind; a separate baseline per bundled utility satisfies no additional objective. [a]
- **Writing a separate baseline for each application inside a single office or productivity suite.** One baseline for the suite as a whole meets the objective; per-application baselines inside the same suite add no assurance. [a]
- **Insisting on golden-image provisioning when a modern device-management platform already enforces the same settings continuously.** Golden images are one accepted method, not the only one, and continuous enforcement through a management platform meets the same objective with less rebuild overhead. [b]

## Edge cases

- **How much detail a baseline needs for simple, locally installed software with no network connection, database, or data-sharing feature.** Tracking little more than the required minimum version is defensible for software this limited, though this is a matter of degree.
- **Whether multiple server roles sharing one operating system need one baseline or several.** A core baseline for the shared OS settings plus an appendix per distinct server role is a workable pattern, rather than a full separate baseline for each role.
- **How much baselining burden applies to assets that support security but do not themselves handle CUI (most switches, cameras, badge systems).** One position holds that the heaviest burden belongs to assets that process, store, or transmit CUI, with a lighter baseline covering only security-relevant and CUI-adjacent settings for the rest; a stricter reading would baseline these assets the same as CUI-handling ones. Where this comes up, the outcome depends on the assessor.
- **Software pushed to a device after the base image is built (through a software-deployment platform, for example).** It is still part of the baseline; the accepted approach is a separate software baseline incorporated by reference so it does not force a rebuild of the OS baseline. [a]
- **Operating systems that periodically reinstall components a system administrator removed.** The practical response is to pick one endpoint-monitoring tool as the source of truth and reconcile the baseline to what it reports, rather than fighting the platform's own behavior. [a][b]

## Evidence examples

- **Completed hardening checklist with documented deviations and rationale.** [a][b]
- **Group policy settings documentation plus a sample of resultant-policy output from representative systems.** [a][b]
- **Device-management compliance policy and settings-catalog exports.** [a][b]
- **Firewall rule spreadsheet** with rule, ports/protocols, service, business justification, and ticket reference columns. [a][b]
- **Configuration backup or export files paired with a document explaining the intended settings behind them.** [a]
- **Screenshots of key configuration settings.** [a][b]
- **Compliance or benchmark scan report** used as supporting proof wherever a system setting is the best available evidence for a requirement. [b]
- **Device-management reporting showing compliance status across the fleet.** [b]
- **Software baseline entries** documenting name, minimum and maximum version, licensing, and system settings. [a]

## Related requirements

- **3.4.1** supplies the baseline this requirement's settings live inside; a security configuration setting has nowhere to be established without a baseline already in place.
- **3.4.7** frequently shares evidence with this requirement, since a documented firewall rule set answers both which security settings are enforced and which ports, protocols, and services are permitted.
- **3.4.3** and **3.4.4** govern how a deviation or an update to an enforced setting gets tracked and reviewed once the initial baseline is set.
