## Requirement

"Verify and control/limit connections to and use of external information systems."

## Objectives

- [a] connections to external systems are identified;
- [b] the use of external systems is identified;
- [c] connections to external systems are verified;
- [d] the use of external systems is verified;
- [e] connections to external systems are controlled/limited; and
- [f] the use of external systems is controlled/limited.

## Sufficient

- **Build a short, discrete list of the specific business, IT, and security functions that rely on an outside system**, rather than trying to enumerate every website or internet destination a user might reach; practitioner consensus reads this requirement as being about protecting CUI and FCI, not cataloguing all external traffic. [a][b]
- **Categorize each listed connection under the organization's asset-scoping scheme**, a risk-managed asset, a security protection asset, or a CUI asset, so the same list serves both this requirement and scope documentation. [a]
- **Cite a cloud service's federal authorization package identifier as verification evidence**, alongside a subscription record or console access as proof the connection was deliberately established. [a][c]
- **Write a policy naming which cloud services are approved to handle FCI or CUI** and state that anything outside that approved set is prohibited, then back it with firewall rules that actually block the unapproved traffic. [b][d][e][f]
- **Route always-on VPN traffic from remote laptops back through the organization's firewall** so the same control and content-filtering rules apply whether a device is on-site or traveling. [e][f]

## Insufficient

- **Treating a multifactor authentication tool as evidence of identifying external connections**: an authentication tool validates access into the organization's own system, it is not one of the external systems this requirement is tracking. [a]
- **Continuing to rely on a security-protection connection that lacks a federal authorization or CMMC certification once the gap is identified**: several organizations chose to drop such services entirely rather than carry the compliance risk, even though doing so traded away some security capability. [c]
- **Relying only on user training to connect through VPN before starting work, with no technical enforcement**, for a traveling laptop; this leaves a gap since it depends entirely on the user remembering and complying every time. [e]

## Over-engineering

- **Attempting to list every website tied to any business process, including ordinary vendor and banking sites that never carry CUI or FCI**: this inflates the list far beyond what the requirement is asking for. [a][b]
- **Tracking every individual federal government destination separately** when a single general entry covering routine federal destinations and file-transfer tools is enough for the list's purpose. [a]

## Edge cases

- Whether a security-protection connection needs its own federal authorization is being resolved inconsistently across organizations; some are dropping any service that lacks one and accepting a security posture tradeoff to avoid the compliance question, while others continue using such services and rely on other controls to justify the risk, and the outcome depends on the assessor's tolerance for that argument.
- A remote or traveling laptop that only connects through company VPN when a user remembers to, rather than through an always-on tunnel, is treated by some as an acceptable gap covered by training and by others as a real hole in coverage; the stricter reading favors always-on enforcement.
- One line of reasoning holds that this requirement is actually more permissive than scoping guidance for systems the organization still controls, since its objectives ask whether connections are identified, verified, and controlled rather than requiring an absolute technical impossibility of CUI reaching the system; treat this as a genuine tension in how the standards are written rather than as a scoping strategy to lean on.

## Evidence examples

- Spreadsheet listing external connections with a scoping category assigned to each. [a][b]
- Federal authorization package identifier cited next to each cloud service on the list. [c]
- Firewall logs or rules showing content-filtering categories blocked across every network zone. [e][f]
- Policy statement naming approved external systems for FCI or CUI and prohibiting all others. [b][d][f]
- Subscription invoice or console login screenshot for a listed external service. [a][c]

## Related requirements

- 3.1.12 through 3.1.15 govern remote access, one common way of reaching or being reached by an external system.
- 3.5.3 requires multifactor authentication for network access, which protects the organization's own system rather than verifying the external ones this requirement tracks.
- 3.13.11 sets the encryption bar that a qualifying cloud service's authorization is built on.
