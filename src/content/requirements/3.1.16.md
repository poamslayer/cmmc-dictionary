## Requirement

"Authorize wireless access prior to allowing such connections."

## Objectives

- [a] wireless access points are identified; and
- [b] wireless access is authorized prior to allowing such connections.

## Sufficient

- **Accept a pre-shared key as adequate authentication and encryption**: assessors care that a method authenticates and encrypts, not which specific standard does it, so a standard pre-shared key configuration is enough on its own. [a][b]
- **Distribute the key through an endpoint management tool** so end users never see or type it directly, satisfying authorization without depending on user discretion. [b]
- **Pre-configure wireless credentials during device build** so the end user has no way to obtain or share them, paired with a policy prohibiting personal devices on the internal network. [b]
- **Treat wireless as a plain transport layer in a cloud-only architecture**, since the meaningful protection is already happening above it through encrypted access to cloud services. [a]

## Insufficient

No documented position beyond the Assessment Guide; see confidence.

## Over-engineering

- **Deploying certificate-based network access control specifically for this requirement**: that mechanism is a better fit for the separate identification and authentication requirement, while a pre-shared key with authentication and encryption already satisfies this one. [a][b]
- **Standing up a dedicated segmented wireless security architecture** modeled on federal wireless guidance when a standard pre-shared key configuration already provides the authentication and encryption this requirement asks for. [b]

## Edge cases

- A remote worker's laptop connecting to an uncontrolled wireless network, such as one at a hotel, does not turn that outside network into a CUI asset so long as the traffic crossing it is itself encrypted end to end, whether through a validated VPN or a cloud service's own transport encryption; without that encryption, the analysis changes.
- Whether wireless drops out of this requirement's reach entirely when all CUI traffic already rides validated encryption as a transport is argued from more than one angle: some call it not a CUI asset and therefore not the focus of this requirement, without necessarily marking it not applicable outright.
- A shared pre-shared key posted somewhere visitors could see, alongside a separate guest network with no path to internal resources, was still treated as meeting the letter of this requirement, even though the practice drew separate criticism on plain security grounds.

## Evidence examples

- Wireless configuration screenshot showing a pre-shared key protocol enabled. [a][b]
- Endpoint management policy distributing the wireless key so users cannot view it directly. [b]
- Written policy describing which devices may join wireless and the authorization step required first. [a][b]
- Network diagram or asset list showing wireless access points and which segment each serves. [a]

## Related requirements

- 3.1.17 adds the specific authentication and encryption protections this requirement's authorized access must use.
- 3.1.18 governs the mobile devices that most often connect over the wireless access this requirement authorizes.
- 3.5.2 covers device and user identification and authentication more broadly, which is the better home for certificate-based network access control.
