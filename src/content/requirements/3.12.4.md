## Requirement

"Develop, document, and periodically update system security plans that describe system boundaries, system environments of operation, how security requirements are implemented, and the relationships with or connections to other systems."

## Objectives

[a] a system security plan is developed;
[b] the system boundary is described and documented in the system security plan;
[c] the system environment of operation is described and documented in the system security plan;
[d] the security requirements identified and approved by the designated authority as non-applicable are identified;
[e] the method of security requirement implementation is described and documented in the system security plan;
[f] the relationship with or connection to other systems is described and documented in the system security plan;
[g] the frequency to update the system security plan is defined; and
[h] system security plan is updated with the defined frequency.

## Sufficient

- **A spreadsheet-format system security plan, organized by domain or family across separate tabs, in place of a single narrative document.** Practitioner consensus treats format as a free choice; what matters is that the required information is present and findable, not whether the document is a spreadsheet or prose. [a][e]
- **A short narrative for each requirement addressing every objective letter directly, with supporting policies and procedures referenced rather than reproduced in full.** This structure is described as the preferred shape: dense enough that an assessor can find the answer to each objective quickly, with detail pushed to referenced documents. [e]
- **A description of the operating environment covering the three asset dimensions scoping guidance recognizes: the people who touch the environment, the technology in use, and the physical facilities involved.** A narrative naming the nature of the business, how information moves through sales, engineering, and production activity, the physical layout and access controls, and the mix of cloud and on-premises infrastructure is accepted as sufficient depth. [c]
- **Baseline documents covering shared, service-level detail for a cloud platform, incorporated into the system security plan by reference** rather than repeating the same configuration narrative across every requirement that touches that platform. This layered, "striped" approach by infrastructure tier is accepted as a way to show defense-in-depth without duplication. [e][f]
- **A defined update frequency, stated explicitly, with the plan actually updated on that schedule.** [g][h]
- **Diagrams and visual aids supporting the written boundary and environment descriptions.** Assessment Guide discussion and practitioner consensus both treat diagrams as valuable supporting evidence rather than a substitute for the written plan. [b][c]

## Insufficient

- **An unusually short plan, well below the length of the base template, with no substantial body of supporting documentation behind it.** A plan far shorter than expected is treated as an early warning sign unless hundreds of pages of referenced policies, procedures, and configuration records exist to back it up. [a][e]
- **A plan that only points elsewhere for every answer, forcing an assessor to hunt through other documents to find what is being assessed.** A reference-only structure that never states the answer directly is called out as a poor pattern, because it pushes the burden of finding the actual implementation onto the reader. [e]
- **A plan padded with excessive, unfocused detail that has nothing to do with any specific objective.** Filling the plan with unrelated material makes it harder, not easier, to find the substance an assessor is checking for; the goal is a plan dense with relevant fact, not simply a long one. [e]

## Over-engineering

- **Maintaining the plan in two parallel formats, such as a full narrative document and a full spreadsheet version, kept in sync with each other.** Objective [a] is satisfied by one properly maintained plan in a single chosen format; maintaining a second parallel copy adds maintenance burden without satisfying any additional objective. [a]
- **Tracking spreadsheets with far more columns and metadata than an assessor would ever need to evaluate an objective.** Extra tracking fields beyond what is needed to show the objective, method, and evidence for each requirement add overhead without satisfying any additional objective. [e]

## Edge cases

- **How to restructure system security plan boundaries when migrating from on-premises infrastructure to a cloud infrastructure-as-a-service model.** One approach keeps separate, system-specific plans tied to each application; another consolidates everything under a single cloud-platform plan with implementation variations described per requirement. Both are workable; the choice comes down to which is more manageable given how much service-level detail can be pushed into a shared baseline document referenced by the plan.
- **What the operating-environment objective is actually asking for.** This objective is not asking which operating system runs on a given asset; it is asking for the operational context, meaning how and where information is handled, the physical environment, and how users actually work day to day.
- **Whether Contractor Risk Managed Assets and Specialized Assets need their own documentation inside the plan.** At Level 2, these asset categories are expected to be documented within the plan itself, even though they are not individually assessed against every requirement the way a CUI Asset is.

## Evidence examples

- **The system security plan itself**, in whatever format the organization has chosen, addressing every objective letter. [a][b][c][d][e][f][g][h]
- **A documented list of requirements identified and approved as not applicable**, with the approving authority named. [d]
- **Network and boundary diagrams supporting the written system-boundary description.** [b]
- **A narrative describing people, technology, and facilities in the operating environment.** [c]
- **Baseline configuration documents for shared platform services, referenced from within the plan.** [e][f]
- **A stated update frequency in policy, plus version history or revision records showing updates occurred on that schedule.** [g][h]
- **Supporting policy and procedure documents referenced by, but not duplicated inside, the plan.** [e]

## Related requirements

- **3.12.1** and **3.12.3** both depend on this requirement's plan as the baseline against which periodic assessment and ongoing monitoring are measured.
- **3.12.2** ties back to this requirement's documented, approved implementation methods when identifying deficiencies to correct.
- **3.13.2** and other system and communications protection requirements rely on this requirement's boundary and environment descriptions to establish what is actually in scope.
- **3.1.1** and the broader asset inventory feed this requirement's boundary and relationship descriptions with the concrete list of what the plan needs to describe.
