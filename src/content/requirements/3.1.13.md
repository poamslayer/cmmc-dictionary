## Requirement

"Employ cryptographic mechanisms to protect the confidentiality of remote access sessions."

## Objectives

- [a] cryptographic mechanisms to protect the confidentiality of remote access sessions are identified; and
- [b] cryptographic mechanisms to protect the confidentiality of remote access sessions are implemented.

## Sufficient

- **Reserve FIPS validation for the layer that actually carries CUI**: a standard encrypted, non-FIPS session is acceptable when no CUI moves during it, since FIPS-validated cryptography is required to protect CUI in transit outside the protected environment, not every remote session (Assessment Guide discussion). [a][b]
- **Accept a layered connection as compliant if one layer is validated**: a VPN riding on top of a FIPS-validated TLS session end to end is sufficient as long as one layer in the path carries the validation. [b]
- **Let a government cloud tenant's own encryption cover CUI in transit**: when the only relevant CUI flows through a tenant that already runs FIPS-validated encryption, the endpoint still needs its own FIPS mode for data at rest, but the tenant covers the session itself. [a][b]
- **Allow non-FIPS remote administration when CUI never appears in the session**: SSH-based maintenance of a CUI asset does not need FIPS validation if no CUI is accessed or transmitted, backed by audit logs proving that. [b]

## Insufficient

- **A policy alone that forbids remote CUI access**: practitioner consensus is that this requirement still applies regardless of what the policy says users may not do. [a][b]
- **An unrestricted session from an unmanaged device**: a remote desktop connection that is not configured to limit traffic to keyboard, video, and mouse pulls the connecting device into scope rather than protecting confidentiality. [b]
- **A commercial cloud proxy with no federal authorization**: routing CUI through a tunneling or proxy service that lacks a moderate-level federal authorization breaks the validated chain, even if only briefly for routing. [b]
- **Disk encryption on an endpoint not running in FIPS mode**: the encryption implementation itself is then unvalidated, regardless of what algorithm it uses. [b]

## Over-engineering

- **Requiring FIPS validation for every remote administrative session**: the requirement protects the confidentiality of CUI in a remote session, not every remote session that touches an in-scope device. [b]
- **Layering a FIPS VPN over a tenant that is already validated end to end**: when the only CUI flow already rides validated cloud encryption, an additional VPN layer adds cost without satisfying anything the tenant does not already satisfy. [b]

## Edge cases

- Whether a virtual desktop client can sit outside this requirement when configured to pass only keyboard, video, and mouse data depends on that restriction being verified and enforced on the hosting side, not merely claimed by the client, and the outcome depends on the assessor's willingness to check the server-side configuration.
- Tunneling a remote desktop session through a separately validated cryptographic module was raised as a possible design, but there was not enough shared technical detail to call it a settled path either way; treat it as unresolved rather than a known-good pattern.

## Evidence examples

- Screenshot of VPN or TLS configuration showing a FIPS-validated cipher suite enabled. [b]
- Registry or group policy export showing FIPS mode enabled on an endpoint. [b]
- Documentation naming which cloud service carries CUI in transit and citing its federal authorization. [a][b]
- Audit log excerpt showing no CUI access occurred during a non-FIPS remote administrative session. [b]

## Related requirements
