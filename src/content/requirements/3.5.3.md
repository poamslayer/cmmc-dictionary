## Requirement

"Use multifactor authentication for local and network access to privileged accounts and for network access to non-privileged accounts."

## Objectives

[a] privileged accounts are identified;
[b] multifactor authentication is implemented for local access to privileged accounts;
[c] multifactor authentication is implemented for network access to privileged accounts; and
[d] multifactor authentication is implemented for network access to non-privileged accounts.

## Sufficient

- **An identity-provider-level or operating-system-level multifactor tool enforcing a knowledge factor plus a possession or biometric factor.** Commercial multifactor platforms used at the OS level do not need a separate government-cloud authorization to serve this role as a security protection asset. [b][c][d]
- **Hardware security keys or passwordless authenticators combining a possession factor with biometrics.** [b][c][d]
- **Push-notification or time-based one-time-passcode authenticator apps for network access.** [c][d]
- **A trusted platform module paired with a PIN for local privileged access.** Some organizations report this combination clearing a government surveillance assessment. [b]
- **Multifactor authentication required to unlock a credential vault that then releases a privileged password.** The reasoning assessors accept: the privileged credential cannot be obtained without first clearing the multifactor step, so the account is effectively protected by it. [b][c]
- **Local administrator passwords stored in a cloud device-management console that itself requires multifactor authentication to reach.** [b]
- **A device certificate combined with a password, particularly where the certificate itself could only be issued through a multifactor-authenticated enrollment process.** [c][d]
- **Single sign-on carried forward from a session established with multifactor authentication**, when the identity platform is configured to require the factor before issuing the session. [c][d]
- **A policy that forces use of the configured multifactor tool, paired with a bounded reauthentication interval.** This has been reported passing a government audit in combination with other controls. [c][d]

## Insufficient

- **Multifactor authentication required only once, at initial device setup or account enrollment.** The objective expects verification tied to ongoing account access, not a one-time enrollment event.
- **Multifactor authentication enabled for cloud email and remote access, with every other network path left unprotected.** Network access covers every network path into the environment, not only the internet-facing ones; this is a common misreading. [c][d]
- **A directory-joined or managed device treated as a factor by itself.** Joining a device to a management platform does not verify who is sitting at the keyboard. [b][c][d]
- **A managed-device compliance check combined with network address allowlisting, with no true knowledge, possession, or inherence factor present.** [b][c][d]
- **Physical location or network address used as a factor.** Location is not something a user knows, has, or is, and current guidance does not accept it as a factor. [b][c][d]
- **A fallback sign-in path that allows a password alone**, left active alongside the multifactor configuration. If a single-factor path remains reachable, the account is not consistently protected. [b][c][d]

## Over-engineering

- **Forcing a fresh multifactor challenge at every screen lock or wake event throughout the day.** The objective addresses account access, not every interaction with a session that already cleared authentication; a bounded reauthentication interval is more proportionate.
- **Requiring multifactor authentication just to join a wireless network.** Wireless network access by itself does not reach the data; the objective targets account access to systems and the information on them.
- **Requiring multifactor authentication on printers.** Isolating the device on its own network segment with management ports closed addresses the practical risk at lower cost than adding an authentication factor to the device itself.
- **Extending multifactor authentication to every downstream application reached from a device that already required it to sign on.** The plain wording addresses account access, not every application reached afterward.

## Edge cases

- **Windows Hello for Business with a trusted platform module and PIN is read differently by different assessors.** Some accept it as a legitimate two-factor combination consistent with current digital-identity guidance; others expect two clearly distinguishable factors demonstrated live, and are reluctant to accept it, especially when only a PIN and not biometrics is configured; the outcome depends on the assessor.
- **Whether a forced password-reset interval must accompany multifactor authentication is unsettled.** Some organizations report passing with no forced password expiration once multifactor authentication is in place; others report an assessor insisting on some scheduled reset regardless of multifactor status; the outcome depends on the assessor.
- **Multifactor authentication is not expected on the mobile device itself**, since a smartphone is not treated as a network device or information system for this purpose; accessing a network resource from that phone still triggers the network-access objective.
- **Operational technology and other specialized assets that cannot technically run multifactor authentication** can be documented as an enduring exception with compensating controls rather than forced into a mechanism the hardware cannot support.
- **How far the administrative-access objective reaches into network devices varies by assessor.** Command-line and management-portal access to privileged network-device accounts is privileged network access needing multifactor authentication or a vaulted-credential path; some organizations report an assessor extending this to every network device including the firewall, others report it applied only to the primary perimeter device; the outcome depends on the assessor.
- **Switching from a non-privileged to a privileged account mid-session is expected to trigger its own multifactor prompt**; carrying forward the non-privileged session's authentication to cover the elevation is not consistently accepted.
- This requirement is commonly failed at assessment, most often on the network-access-only misreading and the local-privileged-account gap.

## Evidence examples

- **Configuration export of a policy enforcing multifactor authentication for network access.** [c][d]
- **Configuration showing multifactor enforcement for local privileged sign-on.** [b]
- **Authentication logs showing multifactor events tied to specific accounts.** [c][d]
- **Credential vault configuration showing multifactor is required to retrieve secrets.** [b][c]
- **Enrollment record for hardware keys or biometric authenticators.** [b][c][d]
- **Documentation of a required reauthentication interval alongside the multifactor configuration.** [c][d]
- **Live demonstration of the multifactor prompt during the assessment**, prepared in advance for accounts using a long "remember this device" window. [b][c][d]

## Related requirements

- **3.5.1** and **3.5.2** identify and authenticate the same accounts this requirement then subjects to a second factor.
- **3.1.12** through **3.1.15** govern the remote access sessions where network-access multifactor authentication most often applies.
- **3.7.5** requires multifactor authentication specifically for remote maintenance sessions, a narrower case of the same control.
- **3.5.7** governs the password factor itself, when a password serves as one of the two or more factors in use.
