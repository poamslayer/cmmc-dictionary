## Requirement

"Terminate (automatically) a user session after a defined condition."

## Objectives

[a] conditions requiring a user session to terminate are defined; and
[b] a user session is automatically terminated after any of the defined conditions occur.

## Sufficient

- **Defining a user-initiated logoff itself as one of the terminating conditions.** Stating that clicking log off terminates the session has been accepted in Level 2 assessments as a legitimate defined condition, even without an inactivity timer layered on top. [a][b]
- **Defining account disablement as the terminating condition.** An organization built around a cloud identity platform passed an assessment on the basis that a session ends when the underlying account is disabled, with no separate inactivity timeout defined at all. [a][b]
- **A scheduled, organization-wide reboot on a recurring cadence** (for example weekly). This has the side effect of terminating every active session on that cycle, alongside its general maintenance value, and has been used as the defined mechanism. [b]
- **A scheduled daily log-off task run across servers and endpoints.** This kind of scheduled forced log-off has been discussed as workable, provided the organization can actually execute the schedule it defines. [a][b]
- **A cloud productivity platform's own logout behavior**, where the platform ends the user's session on receiving a logout request, has been cited as the mechanism behind a passing assessment for that portion of the environment. [b]

## Insufficient

No documented position beyond the Assessment Guide; see confidence.

## Over-engineering

- **A short, fixed idle-timeout (for example two hours) applied uniformly to standard workstations that are not part of a virtual desktop environment.** A short universal timeout on ordinary endpoints creates unnecessary user disruption without a matching gain, compared to a condition tied to logoff or account status.
- **Building now for a future inactivity-maximum requirement that only appears in the next major revision of the standard.** Current-revision assessors are not expected to hold an organization to a future revision's specific inactivity ceiling; it is reasonable to plan ahead, but not necessary to implement it now to pass a current assessment.

## Edge cases

- **Confusing this requirement with network-connection termination.** This requirement is about ending a user's logical session (log off, disable the account, force a password reset), which is a distinct concept from ending a network-level connection; a virtual private network client that times out on its own schedule is addressing the network-connection question, not this one. [a][b]
- **Background processes acting on a user's behalf without direct interaction.** A mail client maintaining a live connection to a cloud mailbox without any user action still counts as a user session for this requirement's purposes, even though no one is actively typing; it is a background process operating under that user's authority. [a]
- **Endpoints and laptops as their own in-scope item.** Whether an organization has defined a distinct termination condition for endpoint devices themselves, separate from whatever is defined for cloud or server sessions, is a question that has been raised without a settled answer; each in-scope item still needs its own answer to this requirement. [a]
- **Whether to adopt the next revision's specific inactivity ceiling early.** Some practitioners favor building toward the more specific future language now, to make current definitions more defensible, while others see no obligation to do so under the current revision; the outcome depends on the assessor and how the organization frames its own defined conditions either way.

## Evidence examples

- **System security plan language stating the specific condition that ends a session** (account disablement, user-initiated logoff, scheduled reboot, or similar). [a][b]
- **A cloud provider's own compliance documentation describing its logout behavior**, cited as supporting evidence for the portion of the environment that provider hosts. [b]
- **Scheduled task or reboot configuration implementing the defined termination condition.** [b]
- **A third-party idle-logoff utility configuration**, used where native scheduling tools proved difficult to script directly. [b]

## Related requirements

- **3.1.10** is the companion mechanism: locking a session in place versus terminating it outright; where locking cannot be implemented, terminating the session under this requirement is the accepted substitute.
- **3.13.9** governs network-connection termination, a distinct question from the logical user session this requirement addresses.
- **3.5.6** (temporary and emergency account management, where applicable) and this requirement both touch account-disablement as a terminating event.
