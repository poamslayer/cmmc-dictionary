## Requirement

"Allow temporary password use for system logons with an immediate change to a permanent password."

## Objectives

[a] an immediate change to a permanent password is required when a temporary password is used for system logon.

## Sufficient

- **Technical enforcement through the identity directory, using a "must change password at next sign-in" style setting.** This is the expected default wherever the account type supports it, since it is straightforward to configure. [a]
- **A written policy instructing immediate password change, used where technical enforcement is not available.** This applies to certain hybrid-identity remote-desktop scenarios where the first sign-on has to reach the virtual desktop before a password can be changed, and to certain device-local accounts that do not support forced change. [a]
- **A clear, specific explanation for why technical enforcement was not used**, when a policy-based approach substitutes for it. Providing that reasoning supports an assessor accepting the workaround. [a]
- **Scoping the temporary credential to a single use, valid only long enough to complete the change to a permanent password.** Assessment Guide considerations frame this as the core behavior an assessor looks for: the temporary password should not remain usable for ordinary logons once the account is active. [a]

## Insufficient

- **A written policy alone, when the account type does technically support forced password change.** If the mechanism is easy to configure, assessors expect it to be configured rather than left to a procedural instruction. [a]
- **No explanation at all for why a procedural control was chosen over an available technical one.** Without that reasoning, an assessor has no way to judge whether the substitute approach is proportionate. [a]
- **A temporary password left valid for ordinary logons well beyond the first sign-on**, rather than expiring once the permanent password is set. Allowing continued use defeats the purpose of forcing an immediate change. [a]

## Over-engineering

No documented position beyond the Assessment Guide; see confidence.

## Edge cases

- **Hybrid identity environments where a user reaches a virtual desktop before the platform allows a password change create a genuine technical gap.** Documenting why enforcement happens after first entry into the virtual environment, rather than before, is accepted when the limitation is explained. [a]
- **Device-local accounts that do not support forced password change at all are handled the same way**, with written instructions substituting for the missing technical control. [a]

## Evidence examples

- **Directory configuration showing a required password change flag set for temporary-password accounts.** [a]
- **Written policy or procedure instructing immediate password change after temporary-password logon**, for account types where technical enforcement is not available. [a]
- **Documentation explaining why technical enforcement could not be applied in a specific scenario.** [a]
- **Test result or walkthrough record from a new-account provisioning check**, confirming that a freshly issued temporary password forces an immediate change and cannot be reused for a later logon. [a]

## Related requirements

- **3.5.7** governs the complexity rules the permanent password must meet once the user changes out of the temporary one.
- **3.5.8** governs whether that new permanent password can match a recently used one; a temporary password typically does not count toward that history the same way.
- **3.5.2** establishes the authentication step a temporary password is standing in for until it is replaced.
- **3.5.1** provides the underlying user identity the temporary password is issued against in the first place.
