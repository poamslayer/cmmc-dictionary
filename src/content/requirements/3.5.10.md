## Requirement

"Store and transmit only cryptographically-protected passwords."

## Objectives

[a] passwords are cryptographically protected in storage; and
[b] passwords are cryptographically protected in transit.

## Sufficient

- **A Windows domain with reversible encryption disabled in group policy**, the expected default configuration; a device-level security baseline can still permit cached logon credentials as long as reversible encryption stays off. [a]
- **Kerberos authentication between a domain-joined Windows device and the domain controller.** Kerberos encrypts the credential exchange by design, satisfying the transmission objective without extra configuration. [b]
- **LDAPS on port 636 for any directory-bound integration**, used in place of unencrypted LDAP; assessors expect the encrypted variant whenever a third-party system binds against the directory. [b]
- **A company-deployed password manager, cloud-hosted or self-hosted, that encrypts its vault at rest and in transit.** Nothing in the objective language rules out password managers, and a mainstream tool that documents its encryption approach is accepted on that documentation. [a][b]
- **Full-disk encryption on the device holding a password file, including a plain text file**, counted as meeting the storage objective because disk-level encryption protects the file at rest. This is a fallback position, not a preferred primary control. [a]
- **A local administrator password rotation and storage tool tied to Microsoft Entra ID or Active Directory**, accepted for local admin credential storage. [a]
- **TLS for web-based authentication, and HTTPS on port 443 for any browser-reachable password manager or admin portal.** [b]
- **An encrypted tunnel wrapping an otherwise plaintext session**, accepted when the tunnel's cryptography is adequate; confirm expectations with the assessor, since the strength of that cryptography is sometimes questioned. [b]
- **Platform or vendor documentation describing how a tool hashes and encrypts stored and transmitted credentials**, submitted as supporting evidence for either objective. [a][b]

## Insufficient

- **Passwords stored in a plain spreadsheet or text file on a device without full-disk encryption.** With no disk-level or file-level protection present, the storage objective is not met. [a]
- **Passwords saved in a browser's built-in credential store as an individual, unmanaged choice**, rather than a company-deployed and documented tool with no organizational record of how that storage protects the credential. [a]
- **Unencrypted LDAP on port 389 used for a directory integration.** The transmission objective requires an encrypted protocol, and plaintext LDAP fails it outright. [b]
- **A password manager or similar tool with no documented, verifiable encryption approach.** Without evidence describing how the tool protects data, neither objective can be confirmed. [a][b]
- **Any password sent over plain HTTP with no encrypted tunnel wrapping the session.** [b]

## Over-engineering

- **Requiring federally validated cryptography for password storage or transmission.** A password protecting a nonfederal system is Security Protection Data, not CUI, and the objective language says nothing about a federal validation standard; that bar belongs to cryptography protecting CUI itself, a separate requirement. [a][b]
- **Requiring a password manager to carry a federal cloud authorization.** That authorization eases inheritance for a provider that already needs it for other reasons, but this requirement does not mandate it, and buying an authorized product solely for this objective adds cost without adding compliance value. [a][b]
- **Disabling cached credentials entirely and forcing full remote reauthentication for every device logon.** A device-level security baseline commonly permits cached logon credentials as long as reversible encryption is off, so blocking cached logons outright goes further than either objective requires and adds friction for staff working away from the office. [a]
- **Applying a short cached-authenticator expiration window meant for a different operating system family to a Windows fleet.** That enhanced control lives in a different platform's hardening guidance, and importing it without cause adds operational burden the objectives do not call for. [a]

## Edge cases

- **Whether a federal cryptographic validation standard applies to password protection is a live point of disagreement.** Some assessors have treated Security Protection Data the same as CUI and expected federally validated cryptography for passwords; the objective text supports no such reading, because a password for a nonfederal system is Security Protection Data, not CUI. The outcome depends on the assessor.
- **A password manager a company selects, configures, and issues accounts for is a Security Protection Asset**, assessed against the requirements its capability touches, this one included. A password manager an employee picks independently, such as a browser's built-in option, sits outside that scope because the company never authorized or deployed it. [a][b]
- **The Assessment Guide's discussion describes one-way hashing as the expected storage method and flags reversible encryption as something to avoid**, but the binding test is the two objective statements, not that descriptive text. A reversible-encryption design, of the kind a password manager uses so it can display or autofill a stored password later, is accepted because the discussion is explanatory, not a separate requirement. [a]
- **Relying on single sign-on to remove most systems from this requirement's reach is workable but incomplete.** Break-glass accounts, service accounts, and local accounts outside the single sign-on flow still need their own cryptographic protection story. [a][b]
- **A coded or obfuscated password recorded on paper**, rather than plain text, is a debated case with no settled position beyond the general expectation that a plaintext password on paper fails the storage objective.
- **Using a cloud tool without a federal cloud authorization remains workable when the company documents shared responsibility for password protection**, for example in a responsibility matrix, rather than an inheritance statement only an authorized provider can offer. [a][b]

## Evidence examples

- **Group policy export showing reversible encryption disabled** for the domain. [a]
- **Identity platform or directory documentation describing password hashing and encryption.** [a]
- **Local administrator password solution configuration documentation** tied to Microsoft Entra ID or Active Directory. [a]
- **Network configuration showing LDAPS on port 636 in use** rather than unencrypted LDAP. [b]
- **TLS or HTTPS configuration evidence for a web-based authentication path**, including a cloud password manager. [b]
- **A responsibility matrix or control benchmark reference for a cloud identity or productivity platform** in scope. [a][b]
- **Vendor documentation on a password manager's encryption model**, covering both storage and transmission. [a][b]

## Related requirements

- **3.5.7** sets the complexity a password must carry; weak complexity makes a properly hashed password easier to crack offline even when this requirement's storage objective is satisfied.
- **3.5.2** authenticates the identity this requirement protects the credential for; authentication depends on the password reaching the system intact and unexposed.
- **3.13.11** applies a federal cryptographic validation standard to protecting CUI itself, the boundary this requirement's over-engineering cases turn on: password protection is not held to that bar because a password is Security Protection Data, not CUI.
