## Requirement

"Monitor, control, and protect organizational communications (i.e., information transmitted or received by organizational information systems) at the external boundaries and key internal boundaries of the information systems."

## Objectives

[a] the external system boundary is defined;
[b] key internal system boundaries are defined;
[c] communications are monitored at the external system boundary;
[d] communications are monitored at key internal boundaries;
[e] communications are controlled at the external system boundary;
[f] communications are controlled at key internal boundaries;
[g] communications are protected at the external system boundary; and
[h] communications are protected at key internal boundaries.

## Sufficient

- **A perimeter firewall or router with deny-by-default rules, an allow list of needed traffic, and logging that supports review.** This is the baseline external boundary implementation across most environments. [a][c][e][g]
- **For an FCI-only environment, a host-based firewall with a deny-by-default posture on each endpoint.** Practitioner consensus treats this as an adequate boundary when there is no CUI in scope. [a][c][e][g]
- **For a cloud-native environment with remote endpoints and no on-premises network, the endpoint's own host-based firewall paired with the cloud platform's own perimeter controls, standing in as the external boundary.** [a][c][e][g]
- **A network segment, such as a restricted virtual LAN, that separates the CUI environment from the rest of the company network**, as the key internal boundary. [b][d][f][h]
- **A documented decision that a small, flat network genuinely has no internal boundary to define.** This is an accepted answer where it reflects the real architecture rather than an omission. [b]

## Insufficient

- **File and folder access lists alone, with no network-level control in place**, in an environment where the network architecture would reasonably call for a firewall. Access lists govern who can read a file; they do not monitor, control, or protect the flow of traffic at a boundary. [c][e][g]
- **Physical security measures, such as badge readers, offered as evidence for this requirement.** Physical access controls address a separate requirement family and do not substitute for network boundary protection here.

## Over-engineering

No documented position beyond the Assessment Guide; see confidence.

## Edge cases

- **Whether a company intranet page or collaboration site with restricted membership counts as a key internal boundary.** One position treats access-scoped groups on such a site as functionally similar to a segmented network zone, since both enforce a logical separation; the opposing position holds that this requirement is about network traffic flow, not document or data permissions, and that a genuine boundary still needs some form of network segregation somewhere in the environment. The outcome depends on the assessor.
- **What counts as the external boundary for a fully cloud-hosted, remote workforce with no physical office network.** The practical answer combines each endpoint's host-based firewall with the cloud platform's own perimeter, since there is no traditional network edge to point to.
- **Whether a cloud platform's own internal separation, invisible to the tenant, needs to be documented as a key internal boundary.** One reasonable position treats this as inherited from the platform and not applicable to document at the tenant level for a small environment; a more conservative position still expects the tenant to describe what it can see and control. The outcome depends on the assessor.
- **Whether a virtual private network is strictly required for remote access.** It is a common way to satisfy this requirement but not the only way; an always-on tunnel, an endpoint firewall, or a cloud-delivered secure access service can each serve the same monitor-control-protect function for remote connections, as long as the chosen mechanism is documented and applied consistently.

## Evidence examples

- **A network diagram showing the external boundary and any key internal boundaries.** [a][b]
- **Firewall or router configuration showing default-deny with explicit allow rules.** [e][f]
- **Logging or alerting output showing boundary traffic is reviewed**, such as blocked-connection summaries or anomaly alerts. [c][d]
- **Endpoint management policy exporting rules that restrict outbound data paths**, for example blocking personal cloud storage sites or removable media at the boundary. [e][g]
- **Encryption or tunneling configuration protecting traffic that crosses a boundary**, such as a site-to-site or remote-access tunnel. [g][h]

## Related requirements

- **3.13.5** adds a specific rule for publicly accessible components: they must sit on a subnetwork separated from the internal network, a more specific case of this requirement's internal boundary concept.
- **3.13.6** specifies the deny-by-default, allow-by-exception posture that gives this requirement's control objectives their operating rule.
- **3.1.20** governs external connections and the use of external systems, which this requirement's boundary controls help enforce.
