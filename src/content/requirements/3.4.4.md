## Requirement

"Analyze the security impact of changes prior to implementation."

## Objectives

[a] the security impact of changes to the system is analyzed prior to implementation.

## Sufficient

- **A dedicated field on the change-request form capturing whether the change alters an existing security configuration setting, introduces a new one, or requires a documentation update.** This has passed a third-party gap assessment as the record of the analysis itself. [a]
- **A short written note, sometimes only a sentence or two and occasionally a short paragraph, describing what was researched about a proposed change's security effect, kept in a spreadsheet alongside the rest of the change record.** Brief as it is, this level of detail has also passed a third-party gap assessment. [a]
- **A change control board where security sign-off is a required step for every change**, rather than a step some changes skip. [a]
- **A patch-management tool evaluated on one specific question: does it tell you whether a given patch actually improves the system's security posture, such as by remediating a named vulnerability, rather than just reporting that a patch is available.** A tool that answers that question satisfies the analysis; one that only lists available patches does not, on its own. [a]
- **Deferring optional feature updates for a period (the Assessment Guide's own example nearby uses a similar delay) while still letting security-only updates apply immediately.** This gives staff time to evaluate a new feature's security effect before it reaches production, while patches addressing known flaws are not held up by that review. [a]

## Insufficient

No documented position beyond the Assessment Guide; see confidence.

## Over-engineering

No documented position beyond the Assessment Guide; see confidence.

## Edge cases

- **Whether automatic updates need to be disabled entirely to satisfy this requirement.** They do not. The working distinction is between updates that add new functionality, which get an impact review (and can be deferred to make time for it), and updates that only remediate a known flaw, which are allowed to apply without that same review since they are already improving the security posture. [a]
- **Systems that fall out of vendor support because their feature-update level lagged too far behind, ending up unpatched with no explicit notice that support had lapsed.** This is a known risk of deferring feature updates for analysis; the mitigation raised in practice is a periodic check of support status rather than assuming a deferred system stays supported indefinitely.
- **A vendor adding a new feature with security implications and no advance notice.** This kind of surprise is the reason cited for deferring feature updates in the first place: the deferral window is what gives staff time to notice and evaluate a change they were not told about in advance.

## Evidence examples

- **Change-request form** with a completed security-impact field. [a]
- **Written impact-analysis note** attached to a specific change record. [a]
- **Change control board minutes** showing a security sign-off step for the change. [a]
- **Test-environment results plus a vulnerability scan** run against an operating-system-level change before it reaches production. [a]
- **Static analysis tool output** run against a software change before deployment. [a]
- **Update-ring or group policy configuration** showing feature updates deferred while security updates remain immediate. [a]

## Related requirements

- **3.4.3** is this requirement's usual home: the review step that requirement tracks and logs is frequently where the security impact analysis actually happens.
- **3.4.1** and **3.4.2** define the baseline and configuration settings that an impact analysis is measured against, since "impact" means a deviation from that established state.
- **3.11.1** and the risk assessment requirements share the same underlying judgment: whether a change increases or decreases risk to the system.
