## Requirement

"Prevent non-privileged users from executing privileged functions and capture the execution of such functions in audit logs."

## Objectives

[a] privileged functions are defined;
[b] non-privileged users are defined;
[c] non-privileged users are prevented from executing privileged functions; and
[d] the execution of privileged functions is captured in audit logs.

## Sufficient

- **Defining privileged functions by category rather than as an exhaustive list of every possible action.** A comprehensive but not overly granular definition (for example, account creation, cryptographic key administration, system-level configuration, disabling security monitoring) is the accepted level of detail, matching how comparable federal access-control guidance frames the same category. [a]
- **Capturing execution without also reviewing it as part of this specific objective.** Objective [d] only requires that the events land in an audit log; reviewing those logs for unauthorized activity is the job of the audit-review and account-management requirements, not this one. [d]
- **Choosing which specific log event identifiers to capture, with a documented rationale for the choice**, rather than following any single mandated list. A reasonable, explainable selection has been accepted, particularly for very small organizations, as long as the reasoning is visible. [d]
- **Scoping this requirement to systems that actually handle CUI first.** Where a device does not store, process, or transmit CUI, this requirement does not reach it; local administrative rights on an out-of-scope development machine sit outside the requirement entirely. [a][b]

## Insufficient

- **Defining privileged functions in a way that is circular with the access-control mechanism itself** (for example, defining a privileged function only as whatever a particular authentication prompt happens to grant). This does not actually identify the functions; it just restates the mechanism. [a]
- **Continuing to run an application that has privileged capability but no logging option and no way to tie its accounts to a central directory**, when a viable alternative exists. Unless the application is mission-critical with genuinely no substitute, this gap is treated as something to fix by replacing the tool rather than working around. [d]

## Over-engineering

- **Publishing specific log event identifiers inside company-wide policy.** Policy should state the expectation to log privileged functions; the specific identifiers belong in a technical baseline document, not the policy itself, so the policy does not need to be revised every time a technical detail changes.
- **Staffing continuous, real-time human review of every privileged session recording.** This goes well beyond what the requirement asks; capturing the log entry is the requirement, not live human monitoring of every event.
- **Attempting to enumerate every single action a privileged account could ever take.** A category-based definition (system administration, security administration, cryptographic key management, and similar groupings) is sufficient; an exhaustive action-by-action list is unnecessary and impractical to maintain.

## Edge cases

- **Developers holding local administrative rights on machines that do not touch CUI.** Because the requirement only applies to systems that store, process, or transmit CUI, this scenario sits outside its scope; the priority is addressing privileged-function logging on the CUI assets first. [a][b]
- **Applications with a privileged web interface but no native logging and no way to federate with a central directory.** Workable mitigations include limiting network access to the interface to specific approved addresses, layering in an authentication gate that itself logs who reached the privileged function, or replacing the application if it is not mission-critical. [c][d]
- **Environments that have fully prevented non-privileged users from ever reaching a privileged function.** Even where prevention is airtight, the organization still needs to log privileged-function execution by the privileged users who legitimately use it; prevention does not remove the logging objective. [d]

## Evidence examples

- **A category-based written definition of privileged functions** for the organization's own environment. [a]
- **A documented, rationale-backed list of the log event types captured for privileged activity.** [d]
- **Technical baseline documentation listing specific event identifiers**, kept separate from the policy document itself. [d]
- **Configuration showing role-based restriction preventing non-privileged accounts from reaching administrative functions.** [c]
- **Audit log excerpts showing privileged-function execution captured with the acting account identified.** [d]

## Related requirements

- **3.1.2** defines the transaction and function boundaries this requirement's privileged-function definition draws on.
- **3.1.6** is the mirror image: this requirement blocks non-privileged users from reaching privileged functions, while 3.1.6 keeps privileged users out of non-security functions while unprivileged.
- **3.3.1** and **3.3.2** (audit logging) are where the actual mechanics of capturing and retaining the log entries this requirement calls for get implemented.
