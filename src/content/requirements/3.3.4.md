## Requirement

"Alert in the event of an audit logging process failure."

## Objectives

[a] personnel or roles to be alerted in the event of an audit logging process failure are identified;
[b] types of audit logging process failures for which alert will be generated are defined; and
[c] identified personnel or roles are alerted in the event of an audit logging process failure.

## Sufficient

- **A monitoring platform configured to raise an alert when a watched log source stops sending events within a set window**, routed to a security team that investigates and works with the system owner to find the cause. This pattern has carried an organization through a federal assessment. [b][c]
- **A recurring check-in query with an alerting rule that fires when an endpoint fails to report for several consecutive days**, sized to account for normal off-hours or weekend shutdowns. Practitioner consensus treats this as more than adequate. [b][c]
- **Bidirectional reachability alerting between a firewall and its log destination**, alerting on either side when the other becomes unreachable. [b][c]
- **A scheduled check counting records received against a defined threshold, alerting when the count falls below it**, including a threshold of zero, since logs stopping entirely is itself the failure condition this requirement is about. [b][c]
- **A hardened operating-system setting that halts a system if it becomes unable to log security events**, paired with a network alert for when that system becomes unreachable. On its own this pairing looks reasonable, though see over-engineering for the caveat that comes with the halt behavior. [b][c]
- **Inheriting this control from a cloud provider's own compliance posture for a fully managed software-as-a-service component**, documented in the SSP with a reference to where the provider addresses the equivalent control in its own authorization package. Infrastructure and platform services in the same cloud are typically not covered by this inheritance and need their own alerting. [a][b][c]

## Insufficient

- **Configuring an alert with no accompanying documentation of who receives it or what triggers it.** All three objectives have to be visible: an alert alone, without an identified recipient and a defined failure type, does not complete the requirement.
- **Manually checking whether logs arrived, instead of an automated push.** Manual spot-checking is not a substitute for a generated notification, such as an alert, email, text, or ticket, that reaches a responsible person without anyone having to go looking for it.
- **Assuming a cloud provider covers this requirement without confirming it.** The organization stays responsible for proving every requirement is met, whether directly or through a provider; that means obtaining the provider's own responsibility documentation, confirming what it actually covers, and filling any gap itself.

## Over-engineering

- **Treating an automatic system shutdown on logging failure as the default, universally correct response.** Shutting a system down is not always the right move; incident responders may need to observe the system in its current state, and other isolation techniques can preserve more value than an immediate halt. This choice is worth a conversation with someone versed in incident response rather than a blanket policy.
- **Building individual per-endpoint alerting for devices that are normally off outside business hours, to the same standard as an always-on server or firewall.** Reviewers generally do not expect that level of granularity for part-time devices; a reasonable check-in window sized for normal downtime satisfies the intent at much lower operational cost.

## Edge cases

- **Mobile devices under a management-container model.** Where mobile devices are not a source of direct audit logs under the organization's own logging scope, and a mobile application management tool reports on its own health, that reporting has satisfied this requirement for that device population without adding endpoint-level audit logging to the phone itself.
- **Systems expected to run continuously versus systems expected to be off part of the time.** Reviewers distinguish between always-on assets, such as firewalls and servers, which warrant tight per-system alerting, and part-time assets, such as laptops, where a longer check-in window tuned to normal usage patterns is the accepted approach.
- **A third-party monitoring tool that cannot natively alert on a specific log source's ingestion failures.** Where a direct alert is not available, a recurring report that would surface an ingestion error code has been proposed as a workaround, though its acceptance is not settled; the outcome depends on the assessor.
- **Whether infrastructure or platform services hosted inside an otherwise compliant cloud environment inherit this control.** Software-as-a-service components are more commonly treated as inherited from the provider's own compliance posture; infrastructure and platform services in the same cloud generally are not, and need the organization's own alerting built and documented separately.

## Evidence examples

- **A monitoring platform's alert rule configuration for a log source that has gone silent.** [b][c]
- **A screenshot or record of a delivered alert reaching the identified recipient.** [a][c]
- **A hardened setting configured to halt logging failure on a host**, where that approach is used. [b]
- **A firewall-to-log-destination reachability alert configuration.** [b][c]
- **A cloud provider's own compliance documentation**, showing where it addresses the equivalent control for an inherited service. [a][b][c]
- **Documentation identifying which personnel or roles are the alert recipients.** [a]
- **A policy or procedure defining the types of logging failures that trigger an alert.** [b]

## Related requirements

- **3.3.1** is the logging process this requirement watches for failure; without defined audit logs to fail, this requirement has nothing to alert on.
- **3.6.1**, incident handling, is often the receiving process for an alert this requirement generates, since a logging failure can itself be a security event worth investigating.
- **3.3.3** reviews and updates what gets logged; this requirement makes sure the organization knows when that logging stops working at all.
