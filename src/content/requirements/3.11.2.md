## Requirement

"Scan for vulnerabilities in organizational systems and applications periodically and when new vulnerabilities affecting those systems and applications are identified."

## Objectives

[a] the frequency to scan for vulnerabilities in organizational systems and applications is defined;
[b] vulnerability scans are performed on organizational systems with the defined frequency;
[c] vulnerability scans are performed on applications with the defined frequency;
[d] vulnerability scans are performed on organizational systems when new vulnerabilities are identified; and
[e] vulnerability scans are performed on applications when new vulnerabilities are identified.

## Sufficient

- **Scanning the whole network boundary to boundary**, not only the assets formally classified as CUI Assets. Practitioner consensus reads the scope of this requirement as reaching every asset that can affect the security of the CUI environment, including risk-managed assets that sit unseparated from it. [b][c]
- **Credentialed scanning enabled everywhere it is technically supported**, since an unauthenticated scan is materially weaker at surfacing application-level flaws than a scan run with credentials. [b][c]
- **An annual scan cadence as the practical floor, with quarterly or more frequent scanning read as the safer norm.** Continuous or near-daily automated scanning goes beyond what the requirement demands. [a]
- **A documented process for updating the scanner's vulnerability database before each scan**, so each run checks against current signatures rather than a stale set. [d][e]
- **A defined process for tracking newly disclosed vulnerabilities and acting on the ones relevant to the environment**, evidenced by a subscription to a public advisory feed, a documented investigation, and a record of the action taken. [d][e]
- **A written, defensible position on equipment that cannot support credentialed scanning**, such as a firewall that must stay in a hardened mode incompatible with the access credentialed scanning needs, paired with an alternative check such as manual firmware version review. Framing the exception as "credentialed scans enabled everywhere the equipment supports it" reads far better to an assessor than an unexplained gap. [b]
- **Documented network segmentation that reduces exposure** as one factor supporting a lighter scanning posture for a given segment, alongside the scanning that still occurs.

## Insufficient

- **Scanning only the assets formally labeled CUI Assets while leaving the rest of the shared network unscanned.** Most assessors expect the scan to reach the full network the CUI environment sits on, not a curated subset. [b]
- **Scanning only convenient, office-based systems while skipping remote or traveling endpoints.** The scan population must account for the full remote and mobile fleet. [b]
- **Treating patch management alone as satisfying this requirement.** Patch management and vulnerability scanning are separate requirements; doing one does not stand in for the other. [b][c]
- **Scanning the operating system layer while leaving internet-facing applications, such as a hosted web application, unscanned.** Applications with open network listeners carry distinct risk from the underlying OS and need their own scan coverage. [c]
- **Having no evidence of a scan run in response to a major, publicly disclosed vulnerability that affected the environment.** Objectives [d] and [e] expect a demonstrable response to specific new vulnerabilities, not just the periodic cadence. [d][e]

## Over-engineering

- **Deploying dedicated vulnerability scanning tooling to mobile devices.** No widely reported assessed environment extends formal vulnerability scanning to phones, and doing so goes beyond common practice. [b]
- **Running automated scans within a day or two of every new vulnerability disclosure.** Near-continuous scanning exceeds what the requirement calls for; a defined periodic cadence plus a response process for newly identified vulnerabilities is enough. [a][d][e]
- **Building a fully manual daily threat-intelligence review process, with saved correspondence as evidence, ahead of what an automated scanner update cycle already provides.** This can be a reasonable extra layer but is well beyond the baseline the objectives require. [d][e]

## Edge cases

- **Whether mobile devices must be scanned.** One position holds that mobile devices fall outside the definition of an organizational information system and are therefore excluded from this requirement; the opposing intuition is that a phone that regularly accesses CUI is functionally part of the system. Most organizations currently do not run formal vulnerability scans against phones, but the outcome depends on the assessor.
- **Whether printers and similar networked peripherals need the same scan coverage as computers.** Assessment Guide discussion names networked printers, scanners, and copiers as devices that should not be overlooked, yet practitioner experience is mixed on how strictly this gets enforced, and the outcome depends on the assessor.
- **How to document scanning for a cloud-hosted service where scans run on an automatic, vendor-managed schedule.** Manually triggering a scan may not be possible, so organizations instead document how the provider keeps its own scanning current as the basis for meeting objectives [d] and [e].
- **How to handle network devices that a chosen scanner cannot authenticate against.** A basic unauthenticated scan combined with manual firmware version verification is a workable substitute when a documented technical reason blocks credentialed access.

## Evidence examples

- **Scan reports timestamped to the defined frequency**, covering both organizational systems and applications. [a][b][c]
- **Credentialed scan output showing application-level findings**, not just OS-level findings. [c]
- **A record of scanner signature or database updates preceding each scan.** [d][e]
- **A documented response to a specific, named vulnerability disclosure**, including the investigation and the remediation or risk-acceptance decision. [d][e]
- **Remediation tickets or plan-of-action entries generated from scan findings**, connecting this requirement's output to 3.11.3.
- **A written exception for equipment that cannot support credentialed scanning**, with the compensating manual check described.

## Related requirements

- **3.11.1** supplies the broader risk context a scanning program operates inside, though it is a distinct exercise from scanning itself.
- **3.11.3** consumes this requirement's scan output and remediates the findings in line with risk.
- **3.14.1** covers patch management as a separate obligation that scanning results inform but do not replace.
- **3.12.2** turns unresolved scan findings into a tracked plan of action.
