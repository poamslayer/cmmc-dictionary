## Requirement

"Implement cryptographic mechanisms to protect the confidentiality of CUI stored on digital media during transport unless otherwise protected by alternative physical safeguards."

## Objectives

[a] the confidentiality of CUI stored on digital media is protected during transport using cryptographic mechanisms or alternative physical safeguards.

## Sufficient

- **A FIPS-validated hardware-encrypted portable drive that works consistently across operating systems**, using encryption performed by the device's own hardware so the drive presents as an ordinary filesystem to any host, including devices without native drive-encryption support, once unlocked. [a]
- **Alternative physical safeguards used instead of encryption**, such as a locked transport case moved by an authorized escort to a facility with secure storage at the destination. Accepted as a substitute for cryptographic mechanisms when the requirement's own text allows it. [a]
- **Skipping encryption for transfers that stay entirely inside the organization's physical perimeter.** The requirement's own scope does not reach transport within the perimeter, though practitioner consensus still recommends encrypting there anyway, and notes that most common file-transfer protocols already carry transport-layer encryption by default. [a]
- **Protocol-level encryption for internal file-share transfers**, satisfying the transmission half of protecting CUI in transit, particularly where both the server and client are operating in a FIPS-validated mode. [a]
- **Full-disk encryption in FIPS mode on the storage server holding backup data**, which satisfies the storage half of protecting the data, provided the transmission path used to get the data onto that server is separately addressed. [a]

## Insufficient

- **Encryption that is not FIPS-validated, used with no alternative physical safeguard in place.** This does not satisfy the cryptographic-mechanism option; the organization then needs either genuinely FIPS-validated encryption or a documented alternative physical safeguard instead. [a]
- **A hardware-encrypted device whose vendor does not fully support or recommend the operating systems it is actually used with.** Inconsistent cross-platform behavior undermines relying on that device as the sole transport control. [a]
- **Software-based encryption marketed as equivalent to hardware-level portable storage encryption.** Practitioner consensus treats software-only implementations as carrying materially less assurance than a hardware-encrypted device. [a]
- **An application with no built-in encryption capability, used to store CUI on portable media without encryption added elsewhere.** Where the application itself cannot encrypt, the protection has to come from another layer, such as the transport protocol or the operating system. [a]

## Over-engineering

No documented position beyond the Assessment Guide; see confidence.

## Edge cases

- **Finding one encrypted USB device family that works reliably on both Windows and Linux with a completed cryptographic certification.** This remains genuinely difficult; some vendor product lines advertise cross-platform support while their certification is still pending rather than complete, which affects how much weight that support claim should carry.
- **Wireless transport of CUI that is not otherwise encrypted at a higher layer.** If the underlying wireless traffic itself carries unencrypted CUI, the wireless access point needs to be FIPS-capable and actually operating in a FIPS-configured mode, not merely capable of it.
- **Whether FIPS-encrypted media still needs a physical CUI marking.** Guidance on this has shifted: an earlier position treated FIPS encryption as removing an asset from CUI-marking scope, while the current position treats encrypted CUI as still CUI regardless of encryption status. Organizations should mark encrypted removable media consistent with the current position rather than the earlier one.
- **Whether the current allowance to substitute alternative physical safeguards for encryption will continue to be available.** The source material for this requirement names this as a point likely to change once the underlying standard moves to its next revision; organizations relying on physical safeguards instead of encryption should treat that path as time-limited rather than permanent.

## Evidence examples

- **FIPS validation certificate** for an encrypted portable storage device family. [a]
- **FIPS mode configuration documentation** for a storage server. [a]
- **Physical security procedure** for media transport using a locked case and an authorized escort. [a]
- **Network configuration record** showing an encrypted file-transfer protocol in use for internal transfers. [a]
- **Backup solution configuration** documenting encryption settings and the transmission path used. [a]
