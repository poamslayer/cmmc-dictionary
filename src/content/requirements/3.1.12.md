## Requirement

"Monitor and control remote access sessions."

## Objectives

- [a] remote access sessions are permitted;
- [b] the types of permitted remote access are identified;
- [c] remote access sessions are controlled; and
- [d] remote access sessions are monitored.

## Sufficient

- **List every path that reaches in from outside the boundary**: external-facing portals, a third-party VPN service, direct access to an admin console without a tunnel first, a vendor's remote maintenance connection, and screen-sharing tools reaching in from off-site all count and belong on the same list. [a][b]
- **Write down the organization's stance on tunnel treatment**: the Assessment Guide states that encrypted VPN use does not make a connection non-remote, but that adequate provisioning may let an organization treat an established tunnel as an internal network for practical purposes once that reasoning is documented (Assessment Guide discussion). [a][b][c]
- **Enforce a control at the connection point**: a current TLS version, device or domain authentication, and FIPS-validated VPN software are the controls assessors look for at the point of connection. [c]
- **Keep proof the logs were actually reviewed**: a sign-in log review on a set cadence, evidenced by a ticket, an email, or an alert record, not just the existence of a logging tool. [d]
- **Treat direct browser access to a cloud admin console as remote**: an identity or endpoint console reached straight over the internet is remote access, and it needs the same monitoring and control path as VPN-based access. [a][c][d]

## Insufficient

- **Scoping the requirement to CUI transmission only**: practitioner consensus holds this requirement applies whenever remote access reaches an in-scope system for any purpose, including maintenance, not only when CUI is moving. [a]
- **Calling an established tunnel non-remote with no documentation**: assessors have accepted a documented internal-network treatment of an active tunnel in practice, but an undocumented assumption is a different thing, and the outcome depends on the assessor when nothing is written down. [b][c]

## Over-engineering

No discussion found.

## Edge cases

- A permanent tunnel between two company-controlled sites is generally treated as an extension of the internal network rather than remote access, and this reading is not disputed.
- Whether an active VPN session still counts as remote access once the tunnel is established has no settled answer: some treat post-handshake traffic as internal-network traffic, others hold that any path crossing the internet stays remote regardless of tunnel state, and the outcome depends on the assessor.
- A more recent line of argument pushes toward the stricter reading: even an always-on tunnel remains a type of permitted remote access that belongs in the identification objective, and an organization with no physical office should still name the specific transport in use, such as a TLS channel or a cloud gateway, to satisfy that objective.

## Evidence examples

- VPN sign-in log export paired with a dated note or ticket showing the log was reviewed. [d]
- Policy page naming each approved remote access method and the organization's documented position on tunnel treatment. [a][b]
- FIPS-validated VPN client configuration screenshot shown with domain or device authentication settings. [c]
- Alert rule configured to fire on a new VPN sign-in, shown with a sample alert. [d]
