## Requirement

"Separate user functionality from system management functionality."

## Objectives

[a] user functionality is identified;
[b] system management functionality is identified; and
[c] user functionality is separated from system management functionality.

## Sufficient

- **An organization-defined line between an ordinary user account and a privileged administrative account**, stated plainly rather than left implied. Practitioner consensus treats this definition as the organization's own choice to make, as long as it is written down and applied consistently. [a][b]
- **A definition that ties system management functionality to a specific account type, such as domain-level administrative access**, with everyday user activity kept on a separate, non-administrative account type. [a][b][c]
- **Logical separation through access control**, most commonly the routine approach organizations use rather than a fully separate physical network for administrative functions. [c]
- **A documented, approved exception process for roles that genuinely need elevated local rights**, such as developers, including a record of who approved it and compensating monitoring such as an alert triggered when a security control is disabled on that account. [c]
- **A live demonstration or screenshot showing an ordinary user account cannot reach a system management function**, as direct proof of the separation. [c]

## Insufficient

- **Generic least-privilege policy language that never names what user functionality or system management functionality actually mean in the environment.** A broad statement about assigning accounts appropriately and following least privilege, with nothing that specifically identifies either category, does not satisfy objectives [a] or [b] and leaves the separation claim unsupported. [a][b]
- **Asserting separation without an account-type or access-control record that shows it in practice.** A definition on paper with no corresponding evidence of enforcement does not reach objective [c]. [c]

## Over-engineering

- **Deploying a dedicated jump host purely to satisfy this requirement.** A jump host is one accepted way to enforce separation, but logical separation through access control is the more common and equally acceptable route; standing up dedicated administrative infrastructure is not required. [c]
- **Building a full privileged-access-management system with checkout workflows for elevated credentials.** This is a reasonable roadmap item but goes beyond what this requirement demands; documented account-type separation is enough. [c]

## Edge cases

- **Whether local administrative rights on a workstation can be defined as non-privileged for a narrow set of roles, such as developers.** One position holds that local admin access is inherently privileged because it lets a user install software and bypass controls a normal user cannot; the opposing position accepts that an organization can define system management functionality around domain-level administration specifically, so long as local admin grants go through a documented exception process with compensating monitoring. The outcome depends on the assessor, though the exception-with-monitoring approach is the more commonly accepted resolution.
- **Very small organizations with only a handful of staff and correspondingly few privileged accounts.** The requirement does not set a minimum headcount, but a tiny team raises practical questions about maintaining a workable separation and, separately, about who reviews logs without also being the only privileged user; both are usually resolved with careful account design rather than treated as an automatic gap.

## Evidence examples

- **A written definition distinguishing user functionality from system management functionality.** [a][b]
- **Account-type documentation showing standard user accounts separate from administrative accounts.** [c]
- **Access control configuration enforcing that separation**, such as group membership restricting administrative tools to a defined set of accounts. [c]
- **A risk exception record for any approved case of elevated local rights**, including approval and any compensating monitoring control. [c]
- **A demonstration or screenshot showing a standard account cannot perform a system management function.** [c]

## Related requirements

- **3.1.5** requires least-privilege access generally; this requirement is the specific application of that principle to separating administrative functionality from user functionality.
- **3.1.2** limits what transaction types and functions an authorized account can perform, which overlaps with how user versus administrative functionality gets defined here.
- **3.3.9** requires at least one privileged account without log access; small environments handling both requirements together need to plan account design across the two.
