## Requirement

"Prevent remote devices from simultaneously establishing non-remote connections with organizational systems and communicating via some other connection to resources in external networks (i.e., split tunneling)."

## Objectives

[a] remote devices are prevented from simultaneously establishing non-remote connections with the system and communicating via some other connection to resources in external networks (i.e., split tunneling).

## Sufficient

- **Split tunneling disabled at the VPN concentrator or firewall for traditional remote access**, so all remote traffic, including traffic bound for the internet, routes through the organization's own controlled path. The Assessment Guide's discussion frames this as the standard remote-device configuration setting the requirement expects. [a]
- **Full-tunnel VPN to the on-premises network, with cloud resources reached through that same tunnel**, giving the organization one controlled path rather than two simultaneous ones. [a]
- **Endpoint-level controls treated as the device's own boundary in cloud-only or SaaS-heavy environments**: a host-based firewall denying unsolicited inbound traffic, endpoint detection and response, DNS or web content filtering, antivirus, and centralized log monitoring, together standing in for the network-level enforcement a traditional firewall would otherwise provide. Assessors have accepted this arrangement across multiple government assessments as meeting the device's own connection boundary. [a]
- **Multiple independently protected connections to a trusted, government-authorized cloud tenant instead of a VPN tunnel**, sometimes called a "securely provisioned connections" approach, when every outbound path is controlled and the destination service's traffic is itself expected and trustworthy. Practitioner consensus treats this as an accepted alternative to full-tunnel VPN. [a]
- **No path for remote access to on-premises resources at all**, achieved by prohibiting remote connections to on-premises systems outright, which removes the two simultaneous paths the requirement is written to prevent. [a]

## Insufficient

- **Asserting that a cloud-only architecture makes the requirement not applicable, with no accompanying technical control.** An assessor has classified ordinary connections to a government cloud tenant as split tunneling and required proof that the connecting device enforces its own boundary; a bare architectural claim did not substitute for that proof. [a]
- **Relying only on a cloud platform's own marketing or architecture statement about eliminating split-tunnel risk, without endpoint configuration behind it.** The statement alone is not evidence an assessor can test. [a]
- **A policy-only statement describing a compensating approach with no technical enforcement behind it.** Assessors have been clear that this requirement, unlike some other frameworks, expects the literal technical control, not an accepted workaround in place of it. [a]

## Over-engineering

- **Standing up a dedicated hosted VPN concentrator in a separate cloud environment, with a static public IP and a conditional-access policy scoping access to that IP, layered on top of endpoint controls that already meet the requirement.** This adds real infrastructure cost without covering more of the objective than host-based firewall, detection, and filtering controls already cover, and it works against the reason an organization moved to cloud-hosted services in the first place.

## Edge cases

- **Whether a user connected directly to a government-authorized cloud tenant counts as "non-remote."** One position, sourced to procurement guidance, treats every user on such a tenant as non-remote and expects them to be blocked from simultaneous internet access at the same time; the community position treats that reading as impractical and instead accepts endpoint controls as meeting the underlying intent. The outcome depends on the assessor.
- **Virtual desktop sessions where the connecting device is asserted to be out of scope.** One position accepts the connecting device as out of scope once the desktop session itself is controlled; a more common position requires the organization to explain how the risk from that connecting device is managed even when it is not itself a CUI asset. The outcome depends on the assessor.
- **Printing to a local or home printer during a remote session with split tunneling disabled.** A documented workaround exists: block device redirection (including printers) in the remote session, restrict printing to directly connected devices, and treat the exception as an authorized data flow rather than leaving it unaddressed.
- **Whether "remote" includes a direct connection from an organization-owned laptop into a controlled cloud tenant.** One reading treats "remote" as anything traversing the internet, including that connection; another reading treats a direct connection to a controlled environment as not remote at all. The outcome depends on the assessor.
- **Rev 3 direction.** Source discussion notes the next revision's objective language adds a qualifier limiting the prohibition to an unauthorized external connection, which would tie the outcome more closely to whether the endpoint's other connections are themselves controlled and authorized. This is a direction to watch, not the current Rev 2 standard this file describes.
- **Platforms that inspect encrypted traffic as part of enforcing this control.** A platform that decrypts and inspects traffic carrying CUI can itself become a system requiring a government cloud authorization for that function, which is a scoping consequence of the chosen implementation rather than a resolution of the split-tunneling question itself.

## Evidence examples

- **VPN or firewall configuration screenshot showing split tunneling disabled at the concentrator.** [a]
- **Endpoint configuration export showing host-based firewall, endpoint detection, and DNS or web filtering enforced on remote devices.** [a]
- **Documented remote access policy stating the split-tunneling configuration and any named exceptions.** [a]
- **Written explanation of how the organization would meet this requirement if it had a path where it applied, for organizations with no on-premises CUI infrastructure to remote into.** [a]

## Related requirements

- **3.13.6** (deny-by-default network communications) sets the general boundary posture that this requirement extends specifically to remote devices with two simultaneous connection paths.
- **3.1.12 and 3.1.13** (remote access monitoring, control, and encryption) govern the remote connection itself, while this requirement constrains what else that connection is allowed to reach at the same time.
- **3.4.6 and 3.4.7** (essential capabilities and nonessential functions) intersect with the printing and local-resource exceptions this requirement forces organizations to document.
