## Requirement

"Review and update logged events."

## Objectives

[a] a process for determining when to review logged events is defined;
[b] event types being logged are reviewed in accordance with the defined review process; and
[c] event types being logged are updated based on the review.

## Sufficient

- **A defined recurring review cadence, at minimum yearly, that checks whether the current set of logged events still meets the organization's needs.** This is the accepted floor for objective [a]; the review itself does not have to find something wrong to count. [a]
- **A work log or change record showing that logging settings were changed to increase true findings or cut down false alarms.** This kind of artifact demonstrates the review actually happened and fed back into what gets logged. [b][c]
- **Meeting notes documenting that the periodic review took place**, even in a period where the review concluded no change was needed. The process being followed is what matters, not that every review produces a change. [a][b]
- **Vendor documentation of what a cloud platform's built-in audit log and endpoint detection tool collects, paired with a documented periodic review confirming those built-in event types still meet the organization's needs.** This combination has been accepted even where the organization cannot directly reconfigure what the platform logs. [a][b]
- **A record of updated baseline configuration, such as a group policy or device management push, following identification of a logging gap.** [c]

## Insufficient

- **Treating a fully cloud-managed logging platform as outside this requirement's reach because its event types cannot be directly reconfigured.** This requirement still applies; the organization is expected to periodically confirm the vendor-provided logging meets its needs, and to supplement it if it does not, rather than treat the platform as exempt.
- **Having logging enabled with no defined process for reviewing whether the right events are being logged.** Logging being turned on is not the same as this requirement, which is about periodically revisiting which events should be logged.
- **No documented review process of any kind.** Without a defined process for when to review, objective [a] is not met regardless of how good the current logging configuration happens to be.

## Over-engineering

No documented position beyond the Assessment Guide; see confidence.

## Edge cases

- **Whether an organization can rely on a cloud platform's out-of-the-box event coverage without ever changing it.** Arguing that the current logging is already sufficient and needs no changes can work as an answer, but it carries more risk than showing at least some improvement effort over time; a reviewer who sees no evidence of active reconsideration may view a static, unchanged configuration skeptically.
- **Whether this requirement is exempt where a fully managed platform does not expose configuration to the customer.** It is not exempt; the accepted path is to document that the vendor-provided logging was reviewed and found to still meet the organization's needs, supplementing with an additional monitoring tool where it does not.
- **How commonly this requirement is missed.** It is commonly failed at assessment, largely from organizations treating the requirement as only about having logs configured rather than about periodically revisiting which events should be logged.

## Evidence examples

- **A work log or change ticket documenting a logging configuration change made after a review.** [b][c]
- **Meeting minutes from a periodic log-review session**, including sessions that concluded no change was needed. [a][b]
- **Vendor documentation describing built-in audit log and detection capabilities**, tied to a documented review of whether they meet organizational needs. [a][b]
- **A group policy or device management export** showing a newly applied logging setting that traces back to a review finding. [c]
- **A documented review schedule or policy** setting a recurring cadence. [a]

## Related requirements

- **3.3.1** establishes the event-type list this requirement periodically revisits and updates.
- **3.14.6** and **3.14.7**, system monitoring, depend on this requirement's review process keeping the logged event set relevant to what needs detecting.
- **3.6.1**, incident handling, both feeds and benefits from this requirement: an incident often exposes a logging gap that this requirement's review process is the mechanism for closing.
