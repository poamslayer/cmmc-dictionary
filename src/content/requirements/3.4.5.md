## Requirement

"Define, document, approve, and enforce physical and logical access restrictions associated with changes to organizational systems."

## Objectives

[a] physical access restrictions associated with changes to the system are defined;
[b] physical access restrictions associated with changes to the system are documented;
[c] physical access restrictions associated with changes to the system are approved;
[d] physical access restrictions associated with changes to the system are enforced;
[e] logical access restrictions associated with changes to the system are defined;
[f] logical access restrictions associated with changes to the system are documented;
[g] logical access restrictions associated with changes to the system are approved; and
[h] logical access restrictions associated with changes to the system are enforced.

## Sufficient

- **Pointing entirely to an existing change-management process, plus physically securing the rooms holding servers, security appliances, and network gear, without a separate access-restriction framework layered on top.** A response along these lines has been accepted during a government-led assessment, on the reasoning that the change process already covers who is allowed to touch what before a change happens. [a][b][c][d][e][f][g][h]
- **Physical security delivered through rooms with restricted entry (a badge reader or a physical key lock) for anything holding servers or network equipment**, documented as part of the facility's access controls rather than as a standalone artifact for this requirement. [a][b][d]
- **Logical security delivered through existing policies, procedures, and training that state who is allowed to make configuration changes**, with the underlying change-management document serving as the definition and the access credentials required to act as the enforcement. [e][f][g][h]
- **A rule that any newly connected device lands on the correct network segment as part of the change process**, tying network placement discipline to this requirement's logical-restriction objective. [e][h]
- **For a fully remote organization, inheriting physical-security assurance from an authorized cloud provider for anything hosted there, plus a written remote-work or acceptable-use policy addressing physical security in an employee's home** (a minimum of one locked door, avoiding being watched while working, and securing a laptop when unattended). Disallowing printing at home is one way organizations have simplified this further. [a][b][c][d]

## Insufficient

No documented position beyond the Assessment Guide; see confidence.

## Over-engineering

- **Documenting every individual physical control, such as the brand and model of every lock, along with a separate definition, documentation, approval, and enforcement statement for each one.** This level of per-device detail goes well past what the objectives ask for; covering the access-restriction categories (who may enter, how entry is documented, how it was approved, how it is enforced) at a facility or room level satisfies the same objectives with far less paperwork.

## Edge cases

- **Whether this requirement covers every change to any organizational system, including something as trivial as a user changing a desktop appearance setting.** One position ties this requirement to security-relevant, baseline-affecting changes only, read alongside the requirements defining security-relevant settings and essential functionality, since an organization has considerable latitude in how it defines what counts as an in-scope change; a broader reading would treat any system change as potentially in scope. The Assessment Guide's own example leans toward a narrower reading focused on who can change baseline configuration or force a deviation from it, but the outcome depends on the assessor.
- **How much this requirement overlaps with change management and with the access-control family.** This requirement reads as duplicative of the change-tracking requirement and of several access-control requirements on first pass; the fact that a change-management-only response has been accepted in an actual assessment indicates the overlap is treated as acceptable rather than as two things that must be separately documented, though this is not guaranteed in every case.
- **Server or equipment closets with only a physical key, no badge reader.** A manual sign-in and sign-out sheet for the key has been used as evidence of physical access logging here, acknowledged as imperfect since compliance with using the sheet is not guaranteed, but treated as a workable substitute for electronic logging at that scale. [b][d]

## Evidence examples

- **Change management process document** that names the access restrictions associated with making a change. [a][e][f]
- **Badge reader logs** for rooms holding servers or network equipment. [d]
- **Key sign-in and sign-out sheet** for closets without electronic access control. [b][d]
- **Network diagram** showing VLAN or segment assignment used to confirm new devices land correctly. [e][h]
- **Credential or admin-rights configuration** showing who can log on to make configuration changes. [f][g][h]
- **Remote-work or acceptable-use policy** addressing physical security in a home office. [a][b][c][d]

## Related requirements

- **3.4.3** is the requirement most often reused to satisfy this one: a change-management process that already names who may propose, review, approve, and log changes typically covers the logical half of this requirement.
- **3.4.2** and **3.4.6** define what counts as a security-relevant setting or an essential capability, which in turn scopes what counts as a change this requirement's restrictions need to cover.
- **3.1.1**, **3.1.2**, and **3.1.5** supply the underlying access-control mechanisms (who is authorized, what they can do, and at what privilege level) that this requirement's logical restrictions draw on.
