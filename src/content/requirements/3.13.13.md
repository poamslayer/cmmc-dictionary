## Requirement

"Control and monitor the use of mobile code."

## Objectives

[a] use of mobile code is controlled; and
[b] use of mobile code is monitored.

## Sufficient

- **A documented decision about which mobile code technologies, browser scripting, browser plug-ins, or document-embedded code, are allowed and which are prohibited.** The decision can be broad or narrow; the objective is satisfied by a deliberate, documented choice rather than by locking everything down. Practitioner consensus treats denying something as an exercise of control just as much as allowing it. [a]
- **Prohibiting legacy browser plug-in technologies organization-wide through centrally managed browser configuration.** [a]
- **Allowing browser scripting broadly, by documented policy decision**, since permitting a technology through a deliberate written decision is itself control. [a]
- **A documented exception allowing a defined group, such as developers, to run additional mobile code technologies their work requires, while the general policy prohibits those technologies for everyone else.** [a]
- **Endpoint anti-malware or browser-security tooling that scans for and alerts on malicious mobile code, with those alerts reviewed as part of routine log or event review.** [b]
- **Firewall-level threat protection that alerts when a user reaches a site serving known-malicious scripted content.** [b]

## Insufficient

- **Treating "mobile code" as synonymous with applications running on a mobile phone or tablet.** It is a different concept from device application management, and answering this requirement with a mobile-device-management policy misses the objective the Assessment Guide's examples describe. [a]
- **Answering this requirement only with a general prohibition on users installing unauthorized software.** That addresses a separate requirement about software installation, not the browser- and document-embedded code technologies this objective names. [a]
- **No documented decision at all about which mobile code technologies are permitted**, leaving both the control objective and the monitor objective with nothing for an assessor to examine. [a][b]

## Over-engineering

- **Attempting to lock every browser scripting technology down to nothing**, when the objective is satisfied by making and documenting a deliberate decision, whether that decision permits or restricts a given technology. A fully locked environment is not what "controlled" requires here.

## Edge cases

- **Developer environments that need to write and run code the organization prohibits for the general user population.** One accepted approach allows a defined subset of users to use specific technologies by documented exception, while the general policy still names what is prohibited for everyone else, and anti-malware coverage still extends to the exception group.
- **Whether a specific browser choice is required, as opposed to leaving the choice open across several managed browsers, is not clearly settled in available discussion.** Treat it as an implementation decision to document rather than a fixed requirement.

## Evidence examples

- **Written mobile code policy naming permitted and prohibited technologies, with any documented exceptions.** [a]
- **Centrally managed browser or endpoint configuration restricting plug-ins and scripting technologies to the policy's decision.** [a]
- **Anti-malware or browser-security tool configuration and its detection or alert history.** [b]
- **Firewall or web-filtering alert logs showing detection of malicious scripted content.** [b]

## Related requirements

- **3.13.14** (VoIP) and **3.13.12** (collaborative device control) sit alongside this requirement as technology-specific control-and-monitor requirements within the same part of the family.
- **3.14.2 and 3.14.4** (malicious code protection and updates) provide the detection capability this requirement's monitoring objective often relies on to identify malicious mobile code.
