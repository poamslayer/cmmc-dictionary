## Requirement

"Control and monitor user-installed software."

## Objectives

[a] a policy for controlling the installation of software by users is established;
[b] installation of software by users is controlled based on the established policy; and
[c] installation of software by users is monitored.

## Sufficient

- **A written policy stating users may not install software without IT permission, backed by removing local administrative rights from standard user accounts so the policy has a technical teeth, and a regular comparison of newly appearing software against change-control records to confirm each addition was approved.** This three-part pairing (written rule, technical enforcement, and a monitoring check) addresses all three objectives directly. [a][b][c]
- **A blocklist-style approach that gives developers administrative rights and lets them install from controlled repositories, in exchange for a stronger monitoring commitment (regularly reviewing software inventories for newly introduced entries) and an active change-control process that retroactively approves additions once confirmed to fit organizational policy.** This is treated as an acceptable trade for the flexibility a development role needs, as long as the monitoring and retroactive approval steps are real and not just stated. [a][b][c]
- **In an environment where no user can install software at all, still standing up a monitoring rule, alert, or report that specifically checks for user-installed software, even if it reliably returns no results.** An empty result from an active check still counts as monitoring; the absence of installs is not itself evidence that monitoring exists. [c]
- **A policy or process of periodically examining user accounts and what is present on them**, which does not necessarily require dedicated software-control tooling to satisfy the requirement, though tooling is the more common implementation. [a][c]

## Insufficient

- **Using a general inventory tool to catalog installed software without reviewing that inventory against a defined blocklist or category of concern.** Cataloging what exists is not the same as controlling or monitoring it against policy; the review step against a defined standard is what the objective is actually asking for. [b][c]
- **Assuming that preventing user installs through an administrative-rights restriction removes the need for monitoring.** Restricting who can install something answers the control objective but not the monitoring one; an assessor can reasonably ask how the organization would know if an installation happened anyway without an active check in place. [c]

## Over-engineering

No documented position beyond the Assessment Guide; see confidence.

## Edge cases

- **Development environments where engineers need local administrative rights and installation flexibility to do their jobs.** The accepted middle ground allows a more open installation posture for developers specifically, provided most tooling comes from controlled repositories, unadvanced-approval installs are still caught by monitoring, and retroactive change-control approval closes the loop; this same openness is not recommended for the general user population. Reducing general email and web browsing on development machines is also raised as a related risk-reduction step, since a compromised development endpoint is a higher-value target than a typical workstation.
- **Air-gapped or internal-only environments.** Limiting email and web access to internal resources reduces the practical risk of unauthorized software reaching a machine in the first place, which can justify a somewhat lighter monitoring burden than a fully internet-connected environment, though the control and monitoring objectives themselves still apply.

## Evidence examples

- **Written policy** requiring IT approval before software installation. [a]
- **Configuration showing standard users lack local administrative rights.** [b]
- **Software inventory report** compared against change-control records to confirm approvals. [c]
- **Monitoring rule, alert, or report** specifically covering user-installed software, including one that shows no findings. [c]
- **Change-control record** showing retroactive approval of a developer-installed tool. [b][c]

## Related requirements

- **3.4.8** is the broader companion to this requirement: where this requirement is limited to whether users can install software, 3.4.8 governs whether software is allowed to execute at all, regardless of who installed it.
- **3.4.1** supplies the software inventory that monitoring for unauthorized installs is compared against.
- **3.1.5** and the least-privilege requirements supply the administrative-rights restriction most organizations use as the technical control half of this requirement.
