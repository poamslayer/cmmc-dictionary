## Requirement

"Terminate network connections associated with communications sessions at the end of the sessions or after a defined period of inactivity."

## Objectives

[a] a period of inactivity to terminate network connections associated with communications sessions is defined;
[b] network connections associated with communications sessions are terminated at the end of the sessions; and
[c] network connections associated with communications sessions are terminated after the defined period of inactivity.

## Sufficient

- **A firewall or VPN concentrator idle-connection timeout, set to a defined value and applied to remote sessions.** Assessors treat this as an ordinary, expected way to meet the requirement. [a][c]
- **VPN session termination at logoff or disconnect**, satisfying end-of-session termination for remote network connections. [b]
- **A single, documented timeout value applied regardless of activity (for example, a full-day disconnect) used in place of a short inactivity window**, when the organization determines a short value is impractical for its remote-access pattern and documents that choice. [a][c]
- **A written policy identifying which network sessions require termination**, paired with user practices such as closing a browser or logging out that end those sessions in the ordinary course of work. [a][b]

## Insufficient

- **No defined inactivity period an assessor can point to, and no configuration implementing one.** Without a documented value, neither objective [a] nor [c] has anything for an assessor to examine. [a][c]

## Over-engineering

- **Configuring automatic daily forced termination of user login sessions as an answer to this requirement**, when that is a separate user-session control satisfied more simply by an ordinary logoff action. Conflating the network-connection control this requirement covers with the user-session control adds configuration effort without covering more of this objective.
- **Building a periodic keep-alive ping to prevent a short VPN inactivity timeout from firing**, as a workaround for an aggressive timeout value. This can undercut the security purpose the timeout exists for rather than satisfy the requirement more thoroughly.

## Edge cases

- **A laptop that leaves the corporate network entirely.** One position treats VPN connect and disconnect as the only session boundary that applies to such a device; an always-on VPN tunneling all device traffic through the firewall is an alternative that gives every firewall session rule an anchor point regardless of where the device is.
- **Whether objectives [b] and [c] are two separate tests or one test connected by "or."** One reading treats them as functionally the same test, following how the parallel 800-53 and the next NIST revision phrase the same idea; this reading is not settled for the current Rev 2 language, so the outcome depends on the assessor, and it is worth confirming directly with an assessor ahead of time if it matters to an organization's implementation.
- **A commonly referenced inactivity value in federal guidance for this kind of session is quite short for typical remote-access use.** Organizations that choose a longer, documented value instead should be ready to explain that choice rather than assume it will pass unquestioned.
- **This requirement governs the network connection itself (the underlying session at the connection level), a different unit from a separate requirement governing when a user's own login session locks or logs off.** Conflating the two in SSP language is a common drafting mistake distinct from actual insufficiency.

## Evidence examples

- **VPN client or concentrator configuration screenshot showing the configured idle-timeout value.** [a][c]
- **Firewall configuration export showing connection timeout settings.** [a][c]
- **Written policy defining which network sessions require termination and the applicable timeout.** [a]
- **Test evidence showing connection state before and after the defined inactivity period, confirming the session actually closes.** [c]

## Related requirements

- **3.1.11** (session termination for user sessions) governs a related but separate unit, the user's login session rather than the network connection; the two are often confused in SSP conformity statements.
- **3.1.18** (mobile device connection control) complements this requirement by governing how a mobile device connects in the first place, while this requirement governs when that connection is torn down.
- **3.13.8** (data in transit) and this requirement both address the lifecycle of a communications session, one its confidentiality and the other its duration.
