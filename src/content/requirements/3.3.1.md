## Requirement

"Create and retain system audit logs and records to the extent needed to enable the monitoring, analysis, investigation, and reporting of unlawful or unauthorized system activity."

## Objectives

[a] audit logs needed (i.e., event types to be logged) to enable the monitoring, analysis, investigation, and reporting of unlawful or unauthorized system activity are specified;
[b] the content of audit records needed to support monitoring, analysis, investigation, and reporting of unlawful or unauthorized system activity is defined; :
[c] audit records are created (generated); :
[d] audit records, once created, contain the defined content; :
[e] retention requirements for audit records are defined; and :
[f] audit records are retained as defined.

## Sufficient

- **A published federal minimum event-type list used as the baseline for what gets logged.** Practitioner consensus treats this kind of published minimum, or a hardening benchmark built from it, as an accepted starting point for defining event types and record content. [a]
- **The organization defines its own logging requirements rather than deferring to an outside mandate.** The requirement's own wording leaves the choice of what to specify to the organization; picking a defensible baseline and documenting it is the accepted approach. [a]
- **A documented retention period of at least ninety days**, discussed as the practical floor for being useful during an investigation; where a platform's native retention is shorter, extending it into a longer-retention store is the accepted fix. [e][f]
- **Extending a short-retention cloud security tool's native log window into a longer-retention workspace or unified log**, so the effective retention meets the organization's own defined period. [e][f]
- **Centrally pushed configuration profiles** that apply a hardened audit policy to managed endpoints, built from a recognized baseline rather than a vendor default. [a][c]

## Insufficient

- **Relying on a security tool's short native retention window alone**, when that window is materially shorter than the organization's own defined retention period and nothing extends it further back. [e][f]
- **The out-of-the-box default audit policy shipped with a common endpoint management baseline, used unmodified.** A bare default of this kind is thin; it does not even reach event types such as removable-media activity that most organizations would consider needed. [a]

## Over-engineering

- **Adding a deep host-level instrumentation agent everywhere as a compliance requirement.** Practitioner consensus treats this as a genuine security enhancement worth the low ingestion cost, but not something objective [a] through [f] demands; a defined and retained set of needed event types satisfies the requirement without it.
- **Logging every file and record modification in the name of this requirement.** This requirement is about confidentiality of CUI, not data integrity; file-manipulation logging at that depth serves an operational integrity goal, not this compliance objective.

## Edge cases

- **Whether laptops count as mobile devices for logging-scope purposes.** Practitioner consensus holds that laptops are not mobile devices under the applicable definition, which is built around small form factor and names examples like smartphones, tablets, and e-readers; a laptop is reasonably placed in its own mobile-computing category in the SSP rather than folded into the narrower mobile-device definition.
- **Whether failed file-access attempts need to be logged on every platform.** Where a documented gap exists between a hardening benchmark and a vendor's own default event tagging, an accepted position is that failed file-access events are not needed if they would not affect investigating an incident that touches the confidentiality of CUI; the organization retains the judgment call on what it specifies as needed. [a]
- **Log ingestion limitations in a government cloud environment compared to a commercial one.** Some ingestion paths available in a commercial cloud environment are not available the same way in a government cloud environment, which can require a different technical path to reach the same defined retention and content goals. [e][f]

## Evidence examples

- **A specification of event types the organization has determined it needs to log.** [a]
- **A definition of what content each audit record must contain.** [a]
- **Screenshots or exports of generated audit records.** [c]
- **Sample audit records showing the defined content is actually present.** [d]
- **A documented retention period.** [e]
- **Configuration evidence showing retention settings that match the defined period.** [f]
- **Endpoint configuration profile exports showing the applied audit policy.** [a][c]
- **Log forwarding or ingestion configuration showing logs reaching a central, longer-retention store.** [e][f]

## Related requirements

- **3.3.2** builds directly on this one: this requirement defines and retains the audit records, and 3.3.2 checks that those records carry enough content to trace an action to a specific user.
- **3.3.3** revisits the event-type list this requirement establishes, on a recurring basis, to confirm it is still the right list.
- **3.3.4** depends on this requirement's logging actually running, since it is the alerting mechanism for when that logging process fails.
- **3.3.5** and **3.3.6** consume the records this requirement creates and retains, for correlation, reduction, and reporting.
