## Requirement

"Employ the principle of least functionality by configuring organizational systems to provide only essential capabilities."

## Objectives

[a] essential system capabilities are defined based on the principle of least functionality; and
[b] the system is configured to provide only the defined essential capabilities.

## Sufficient

- **Naming the enforcement tools used (a configuration-management platform, a directory service, group policy, an application-control feature) in the system security plan and stating that least functionality is enforced through them, without keeping the plan updated with every granular setting inside those tools.** A statement of what is used plus proof it is used has been accepted without requiring the plan itself to mirror every tool setting. [a][b]
- **Tying least functionality directly to the baselines already produced for the baselining and configuration-enforcement requirements: staff review what a system's capabilities are, compare that against what is actually needed, and disable anything enabled by default that nobody needs.** [a][b]
- **A hardware, software, and firmware inventory that adds one extra column stating the business reason each software entry is present, matched up against application-control policy settings as the enforcement evidence.** A reason-for-installation column of this kind is treated favorably as evidence that the review named in [a] actually happened. [a][b]
- **Pre-installed vendor utilities (a recovery tool, an update utility, a runtime dependency) kept on a system because they serve a real purpose, such as recovery, with that purpose written down.** Keeping something that came with the hardware is acceptable once the reason for keeping it around is documented; it is not acceptable to keep it purely because it arrived pre-installed. [a]
- **Provisioning workflow where IT builds and validates that a system meets its baseline before handing it to a user**, treated as itself demonstrating that only essential capabilities reach production. [b]

## Insufficient

- **Treating pre-installed software as automatically acceptable because it came bundled with the hardware.** Coming pre-installed does not exempt software from being identified, justified, and managed the same as anything deliberately added; an organization is still responsible for every capability present on its systems regardless of how it got there. [a]
- **Leaving installed software undocumented when it differs from the established baseline.** A deviation from the 3.4.1 baseline needs the change-tracking and impact-analysis documentation those requirements call for; simply having the software present without that trail does not satisfy this requirement's definition objective. [a]

## Over-engineering

- **Keeping the system security plan updated with every granular setting inside a configuration-management, directory, or group-policy tool.** Naming the tools and confirming they enforce the defined capabilities is sufficient; mirroring every underlying setting inside the plan adds maintenance burden with no assurance gain. [a]
- **Enumerating every individual system capability inside the plan rather than defining the approach and pointing to where the detailed baseline lives.** A defined approach plus a reference to separately maintained baseline documentation meets the objective; a capability-by-capability list inside the plan does not add anything beyond that. [a]

## Edge cases

- **Small organizations combining multiple infrastructure roles on one system, such as running domain and name-resolution services together.** This is acceptable, provided the combination is documented as a defined choice and whatever the combined system is not supposed to do is restricted, disabled, or prevented; those restrictions then become configuration items feeding the baseline requirement.
- **Pre-installed vendor utilities that were not requested but arrived with the hardware.** These are handled no differently than any other software on the system: where a genuine business need exists (recovery tooling is the commonly cited example), write it down and keep the tool; where it differs from the baseline and no such need is documented, treat it as a change needing review rather than something left in place by default.

## Evidence examples

- **System security plan language** naming the enforcement tools and stating that capability review and reduction is performed as part of provisioning. [a][b]
- **Hardware, software, and firmware inventory** with a justification column tied to application-control policy. [a]
- **Application-control (allowlisting) policy exports** showing restrictions aligned with the approved software list. [b]
- **Configuration-management tool exports** (directory, group policy, or equivalent) showing least-functionality settings applied. [b]

## Related requirements

- **3.4.1** and **3.4.2** supply the baseline and enforced settings that this requirement's essential-capability decisions become part of.
- **3.4.3** and **3.4.4** apply when a deviation from the defined essential capabilities (keeping a pre-installed tool, for example) needs to be tracked and analyzed as a change.
- **3.4.7** narrows this requirement's broader "essential capabilities" concept down to the specific programs, functions, ports, protocols, and services that must be restricted to match.
