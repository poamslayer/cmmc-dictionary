## Requirement

"Deny network communications traffic by default and allow network communications traffic by exception (i.e., deny all, permit by exception)."

## Objectives

[a] network communications traffic is denied by default; and
[b] network communications traffic is allowed by exception.

## Sufficient

- **All inbound traffic denied by default on host and network firewalls**, widely treated as the straightforward half of this requirement. [a]
- **Outbound traffic set to deny by default at the general firewall policy level, with specific allow rules layered on top for the ports the environment actually needs.** A documented pass of a Level 2 assessment has relied on exactly this structure. [a][b]
- **Filtering by port rather than by destination address or site.** Port-based rules are treated as meeting the requirement; filtering by destination address as well is a stronger posture than the requirement calls for, not a requirement in itself. [b]
- **A layered rule structure**, such as a baseline set of rules covering essential connectivity, a broader set covering standard application traffic, and role-based additions for specific teams that need extra outbound access. [a][b]
- **Explicit allowance for the high-numbered, short-lived outbound ports operating systems use to complete ordinary connections.** Leaving this range closed breaks normal connectivity and is a common early mistake when first implementing a deny-by-default outbound policy. [b]

## Insufficient

- **Deny rules written as a list of everything to block, with an implicit allow for anything not listed.** This is the reverse of what the requirement asks for: it denies by exception and allows by default, and even where the practical effect looks similar for one protocol, any protocol left off the block list is allowed by default rather than denied by default, which is the opposite posture the requirement calls for. [a][b]
- **A policy that blocks inbound traffic but leaves all outbound traffic unrestricted.** The requirement does not exempt outbound traffic; a deny-by-default posture is expected in both directions. [a]
- **Content filtering that blocks specific categories of destination, such as file-sharing or streaming sites, offered as evidence of a deny-by-default posture.** Blocking specific known-bad destinations is the opposite structure from denying everything and then allowing specific exceptions. [a]
- **Rules that only address one protocol, such as TCP, while leaving other protocols like UDP or ICMP unaddressed.** Anything not explicitly denied is implicitly allowed, so a protocol left out of the ruleset entirely is not actually denied by default. [a]

## Over-engineering

- **Filtering by specific destination address or site in addition to port, offered as the expected baseline.** Port-based filtering is enough to meet the requirement; adding address-level filtering is a stronger posture than what is required, not a missing piece. [b]
- **Writing a separate rule for every individual application executable rather than allowing a port for general use.** Port-level rules covering common traffic, such as standard web traffic outbound for all applications, are accepted practice; per-application rule sets add substantial overhead without being necessary to meet the requirement. [b]

## Edge cases

- **Mobile device operating systems that lack a native deny-by-default firewall capability.** Current practice generally does not extend this specific requirement to phones in the same way it applies to computers, since the underlying platform does not expose the same control; organizations should be ready to explain this gap by platform limitation rather than by omission.
- **Desktop platforms whose native firewall is built around a blacklist model rather than a true default-deny model.** Reaching an actual deny-by-default posture on such a platform typically requires an additional packet-filtering layer rather than relying on the platform's default firewall interface alone.
- **Centrally managed firewall rules that do not appear in a device's local firewall interface.** Where rules are pushed through a policy management platform rather than configured locally, the local graphical interface may not reflect what is actually enforced, and a command-line or platform-native query is often needed to confirm the effective ruleset.
- **Conflicts between centrally pushed rules and a device's own local default rules.** Disabling local rule merging to enforce a strict centrally managed ruleset can, if done without care, remove rules some built-in platform functions depend on, so this change needs staged testing on a limited network profile before wide rollout.

## Evidence examples

- **Firewall policy configuration showing the default outbound action set to deny.** [a]
- **A ruleset showing specific allow exceptions layered on top of that default.** [b]
- **An export or query output from the policy management platform showing centrally pushed rules**, since a locally viewed firewall interface may not reflect them. [a][b]
- **A layered policy structure document** showing a baseline connectivity layer, a general application layer, and any role-based additions. [a][b]
