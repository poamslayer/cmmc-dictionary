## Requirement

"Use session lock with pattern-hiding displays to prevent access and viewing of data after a period of inactivity."

## Objectives

[a] the period of inactivity after which the system initiates a session lock is defined;
[b] access to the system and viewing of data is prevented by initiating a session lock after the defined period of inactivity; and
[c] previously visible information is concealed via a pattern-hiding display after the defined period of inactivity.

## Sufficient

- **Operating-system-level session lock, where every point of access runs through a company-managed operating system.** This has been accepted as covering the requirement end to end when there is no path to the data that bypasses the managed operating system's lock screen. [a][b][c]
- **Host-operating-system session lock covering a local virtual machine that is not reachable remotely.** Because the virtual machine can only be reached through the already-locked host, the host's lock has been accepted as satisfying the requirement for that virtual machine too. [b][c]
- **Substituting session termination for session lock in environments where locking is impractical**, such as key-based remote access with no password prompt to re-lock behind. Terminating the session outright, rather than trying to force a lock screen onto a system that was not built for one, has been treated as an acceptable alternative path, effectively satisfying this requirement's intent through the session-termination requirement instead. [b][c]

## Insufficient

- **Relying only on operating-system lock when a web application is reachable from devices the organization does not manage.** If the organization cannot guarantee that every device reaching the application has its own working session lock, the application itself, or a device in front of it, needs its own inactivity timeout. [b][c]
- **Restricting a web portal to a corporate network address range as the only inactivity control, with no application-level timeout.** Being on the right network address does not guarantee the specific device sitting behind that address has a working lock screen; any device sharing that network segment could reach the login page, so an application-level timeout is still needed. [b]

## Over-engineering

- **Suppressing the content of lock-screen notification previews** (email subject lines, meeting titles, chat previews) when none of that content could actually contain CUI. The requirement is about concealing previously visible information that could be sensitive; where the notification content genuinely cannot carry CUI, obscuring it does not serve this requirement's objective, though it may still be a reasonable general privacy choice.

## Edge cases

- **Web applications accessible from both managed and unmanaged devices.** Where the organization can guarantee every accessing device is company-managed with its own working lock, operating-system lock may be enough; where it cannot make that guarantee, an application-level or gateway-level timeout is needed as well. [b][c]
- **Virtual machines that are remotely accessible rather than local-only.** Once a virtual machine can be reached remotely, the analysis changes: every endpoint capable of reaching it needs its own working lock screen, or remote access to the virtual machine needs to be disabled outright; the local-only exception does not extend to a remotely reachable machine. [b][c]
- **Passwordless or key-based authentication where a traditional lock screen has nowhere to prompt for a credential.** Older configuration guidance used an inactivity timeout setting; newer guidance points toward a screen-lock utility built for that environment. Where neither is a good fit, terminating the session outright under the companion session-termination requirement is the accepted fallback. [a][b]

## Related requirements

- **3.1.11** is the companion mechanism, terminating a session outright rather than locking it, and is the accepted substitute wherever a true lock screen cannot be implemented.
- **3.13.9** covers network-connection termination, a distinct mechanism from the user-session lock this requirement addresses.
- **3.5.3** (multifactor authentication) and this requirement both gate re-entry to an unlocked session, though through different mechanisms.
