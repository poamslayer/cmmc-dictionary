## Requirement

"Authorize remote execution of privileged commands and remote access to security-relevant information."

## Objectives

- [a] privileged commands authorized for remote execution are identified;
- [b] security-relevant information authorized to be accessed remotely is identified;
- [c] the execution of the identified privileged commands via remote access is authorized; and
- [d] access to the identified security-relevant information via remote access is authorized.

## Sufficient

- **Scope this requirement to nonlocal command execution**: a script pushed by an endpoint management tool, an API call that triggers action on a different host, or a centralized configuration run, distinct from a command a user types after already being logged into the target machine through an established remote session. [a]
- **Treat post-connection commands as local for this requirement**: once a user has connected through the organization's approved remote access path, commands run there are not "remote execution" for this requirement's purposes, even though the connection itself is a remote-access question answered elsewhere. [a][c]
- **Define authorized commands by administrative role**: state that everything a given identity-provider role permits is authorized for remote execution under that role, rather than building a line-by-line command list. [a][c]
- **For a fully cloud-hosted environment with no non-remote administration path**, treat access from a managed, enrolled endpoint under conditional access as the organization's working definition of "local," and still separately document which privileged commands and which security-relevant information may be reached that way. [a][b][c][d]

## Insufficient

- **Confusing this requirement with the general definition of remote access**: a user connecting over VPN is a remote-access question answered under a different requirement; whether that same user may then run privileged commands or view security-relevant information is the separate question this one answers. [a][b]
- **Leaving a vector unidentified**: failing to name every way commands can be pushed to a remote host, such as an endpoint push, a patch run, a remote monitoring tool, or SSH access, while only documenting one of them. [a]
- **A broad claim with nothing to point to**: asserting an administrator may run everything their role permits without being able to show what that role actually permits invited a direct challenge in at least one assessment. [a][c]

## Over-engineering

- **Building a line-item list of every command an administrator may run remotely** instead of pointing to the role or group that already defines that set. [a]
- **Solving this requirement in isolation from the rest of the remote access family**: these requirements are meant to be addressed together, not one at a time. [a][b][c][d]

## Edge cases

- Whether a permanent tunnel between two company-controlled sites counts as remote access at all, versus an on-demand user session that clearly does, affects whether commands crossing that link even reach this requirement; the distinction drawn in practice is permanence and organizational control of both ends.
- Reaching a cloud admin console through a browser from an unmanaged location is remote access to a management interface, which practitioners treat as different from pushing a script or command to a remote host, though this line is not applied the same way everywhere, and the outcome depends on the assessor.
- How rigorously an assessor expects a role-based definition of security-relevant information to be spelled out varies; one description called it inherently vague because each organization ends up defining it for itself.

## Evidence examples

- SSP language stating no privileged commands are authorized for remote execution because administration only occurs after connecting to the network, with that connection governed under a separate requirement. [a][c]
- Appendix listing identity-provider privileged roles with a policy statement that commands available to those roles are authorized for remote execution and are logged. [a][c]
- Access control policy naming which roles may view security-relevant information, such as audit log configuration, remotely. [b][d]

## Related requirements

- 3.1.12 defines what counts as a remote access session in the first place.
- 3.1.13 and 3.1.14 protect and route the sessions inside which any authorized remote command execution occurs.
- 3.1.2 limits the transactions and functions authorized users may execute locally, which this requirement extends to the remote case.
