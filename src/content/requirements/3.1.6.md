## Requirement

"Use non-privileged accounts or roles when accessing nonsecurity functions."

## Objectives

[a] nonsecurity functions are identified; and
[b] users are required to use non-privileged accounts or roles when accessing nonsecurity functions.

## Sufficient

- **A written policy stating that privileged users must not use their privileged account for non-security tasks**, reinforced with training. This is consistently treated as the expected form of evidence for this requirement; it is, in practice, primarily a paper-and-training control rather than a purely technical one. [a][b]
- **Defining non-security functions residually**, as everything that is not identified as a security function elsewhere, is an accepted way to satisfy the identification objective without building a second exhaustive list. [a]
- **Role-elevation tooling in a cloud identity platform**, where an account is ordinarily unprivileged and gains administrative rights only for a limited, approved window, satisfies the requirement because the account is non-privileged up until the moment of elevation. [b]
- **Operating-system privilege elevation on Linux-style systems** meets the requirement the same way, as long as users are not routinely running everyday tasks (browsing, general applications) with elevated rights; running as an elevated user only for the specific commands that need it is the accepted pattern. [b]

## Insufficient

- **A single account that carries standing administrative rights and is also used for everyday work.** If the same account and session that does routine tasks also holds administrative permission with no role separation, the requirement is not met. [b]
- **Calling something a best practice without writing it into policy, procedure, or training.** An unwritten expectation, however reasonable, is not evidence; it needs to be documented and reinforced through training. [a][b]
- **Treating unrestricted elevation tooling as sufficient on its own, without describing how permissions are actually restricted.** Simply having an elevation mechanism available does not answer the requirement; what matters is how the organization uses it to keep routine work off privileged sessions, which also touches the privileged-account and privileged-function requirements. [b]

## Over-engineering

- **Requiring a fully separate, individually licensed non-privileged account for every administrative role in every cloud application**, even where a platform's own licensing model makes that impractical. A reasonable, explainable definition of what counts as privileged in that specific tool is enough.
- **Treating a developer's local administrative rights on a workstation as automatically privileged under this requirement**, when those rights only touch functions that are not themselves security functions. The organization has real latitude to define what is and is not a security function in its own environment, as long as the definition is defensible to an assessor.

## Edge cases

- **Linux and similar systems using elevation tooling.** A user with elevation rights is treated as non-privileged right up until the specific moment they invoke an elevated command; the concern is whether they are routinely running ordinary tasks under elevation, not whether elevation tooling exists at all. Elevation can also be scoped to specific commands rather than granting broad root-equivalent access. [b]
- **The relationship between security functions and privileged functions.** Not every security function is also a privileged function; NIST's own language defines the category, and the organization identifies which of its own components fall inside that definition, with an assessor reviewing whether the identification is reasonable and complete. [a]
- **Defining versus identifying.** The organization does not get to redefine what a security function is in the abstract, but it does identify, for its own environment, which specific components meet that definition; this distinction gives real flexibility in how the requirement is documented. [a]

## Evidence examples

- **Written policy prohibiting use of a privileged account for non-security tasks.** [a][b]
- **A table or list identifying security functions**, with everything else understood as non-security by definition. [a]
- **Training materials covering the expected behavior for administrators.** [b]
- **Privileged access management configuration showing time-limited, approval-gated elevation.** [b]
- **Elevation-tool configuration limiting which commands can be run under elevation.** [b]

## Related requirements

- **3.1.5** supplies the privileged-account and security-function definitions this requirement builds on directly.
- **3.1.7** covers the flip side: preventing a non-privileged user from reaching a privileged function at all, and logging it when a privileged function runs.
- **3.4.7** (least functionality) is frequently answered using the same set of definitions used here, since both hinge on what functions exist and who may reach them.
