## Requirement

"Protect wireless access using authentication and encryption."

## Objectives

- [a] wireless access to the system is protected using authentication; and
- [b] wireless access to the system is protected using encryption.

## Sufficient

- **Replace address-based device filtering with certificate-based device authentication** issued by a domain controller, paired with a unique-credential user login before any network resource is reached, and document the organization's own working definition of what counts as authenticated. [a]
- **Use an enterprise wireless mode backed by a directory service**, state plainly that traffic is fully encrypted and only authorized users and devices connect, and separately document how that encryption meets the FIPS-validation standard. [a][b]
- **Rely on FIPS-validated encryption applied at a higher layer than the wireless link itself**, such as a validated VPN, a government cloud tenant's built-in transport encryption, or a file-sharing protocol run in a FIPS mode, so the wireless equipment itself does not need separate validation. [b]
- **Treat wireless as secondary when a file server already runs FIPS mode with signed, encrypted file-sharing sessions**, because the meaningful CUI protection is happening at the file-sharing layer, not the radio layer. [b]

## Insufficient

- **Depending on a consumer-grade wireless platform alone as the only encryption layer for CUI traffic**, when that platform provides no FIPS-validated encryption of its own and nothing above it is validated either. [b]
- **Treating a stronger key-exchange method as itself an answer to FIPS validation**: a more secure way of establishing session keys is not the same thing as a validated encryption module. [b]
- **Leaving CUI on a file server reachable over unencrypted wireless**, protected only by at-rest disk encryption; once that data crosses wireless unencrypted at the transport layer, this requirement is not met. [b]

## Over-engineering

- **Layering a validated wireless encryption product on top of a system where all CUI traffic is already encrypted end to end at a higher layer**, such as a validated VPN or a government cloud tenant. The higher-layer validation already covers confidentiality. [b]

## Edge cases

- Whether wireless itself needs FIPS-validated encryption turns entirely on whether wireless is the layer actually responsible for CUI confidentiality in a given data flow; an organization with more than one CUI data flow has to walk this analysis for each flow rather than assume one answer covers every case.
- Marking wireless not applicable because an environment is cloud-only with no on-premises network is discouraged in favor of explaining why the requirement is met, such as no wireless access existing in the relevant data center, or all traffic being validated above the wireless layer, since a blanket not-applicable finding invites more scrutiny than a documented met finding.
- Open, unauthenticated wireless access is not acceptable under any reading surveyed; every position agrees authentication is required regardless of how the encryption question is resolved.

## Evidence examples

- Wireless configuration screenshot showing an enterprise authentication mode tied to a directory service. [a]
- Certificate template and deployment documentation for device-based wireless authentication. [a]
- FIPS mode configuration on a file server or VPN concentrator that carries the CUI traffic in question. [b]
- CUI data flow diagram showing which layer applies encryption for each path, including any that crosses wireless. [b]
