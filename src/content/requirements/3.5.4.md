## Requirement

"Employ replay-resistant authentication mechanisms for network access to privileged and non-privileged accounts."

## Objectives

[a] replay-resistant authentication mechanisms are implemented for network account access to privileged and non-privileged accounts.

## Sufficient

- **Kerberos-based authentication through a standard directory service.** Its protocol design already resists reuse of captured authentication traffic, so pointing to the directory's authentication configuration is accepted as the evidence. [a]
- **A minimum authentication protocol set to a current, supported version with older, weaker versions disabled, paired with multifactor authentication.** This combination is accepted for network access to both privileged and non-privileged Windows-based accounts. [a]
- **A multifactor solution that issues a unique time-bound code for every authentication attempt and rejects a code once it has been used.** A captured code cannot be replayed successfully under this design, which is exactly what the objective asks for. [a]
- **Hardware or software token-based multifactor solutions**, commonly accepted as meeting this objective on their own. [a]
- **Requiring an encrypted transport protocol for web-based application access**, so that the authentication exchange itself cannot be captured in the clear and replayed later. Assessment Guide example treats this as one piece of a broader replay-resistance posture alongside protocol selection and multifactor authentication. [a]

## Insufficient

- **A single static password sent over the network with no supporting protocol protection or one-time-code mechanism.** A captured password can simply be replayed, and this does not meet the objective on its own. [a]
- **An older, easily replayable authentication protocol left enabled alongside a newer, resistant one.** If the weaker path stays reachable, an attacker can use it instead, so the objective is not met while it remains available. [a]
- **An unencrypted, basic authentication scheme used for a network application**, where the credential exchange travels in a form that can be intercepted and reused. Without an encrypted channel or a one-time credential, the exchange itself gives an attacker everything needed to replay it. [a]

## Over-engineering

- **Capturing and analyzing authentication network traffic with a packet-capture tool to prove a protocol resists replay.** Pointing to the directory service's documented authentication settings is accepted as sufficient evidence; replay resistance is a documented, inherent property of the protocol rather than something that needs to be demonstrated packet by packet.

## Edge cases

- **A cloud provider's own customer-facing compliance documentation for a government-community tenant may describe a stricter, hardware-credential-based authentication expectation than this requirement itself demands.** The applicable bar for this requirement is NIST SP 800-171 Rev 2, not a cloud vendor's own compliance matrix, so a time-bound one-time-passcode approach remains acceptable here even in that kind of tenant.

## Evidence examples

- **Directory service configuration** showing the minimum authentication protocol version and confirmation that older, weaker versions are disabled. [a]
- **Multifactor solution configuration documentation** showing authentication codes are unique per attempt and rejected once used. [a]
- **System Security Plan language** describing the directory service's inherent replay resistance and the multifactor tool's time-bound code behavior. [a]

## Related requirements

- **3.5.2** establishes the authentication step that this requirement then requires be replay-resistant for network access.
- **3.5.3** requires multifactor authentication for the same accounts; the token or code-based factor chosen there often supplies the replay resistance this requirement asks for.
- **3.13.8** and the related transmission-protection requirements address confidentiality of the authentication traffic itself, a related but distinct concern from replay resistance.
- **3.5.7** governs password shape when a password remains part of the authentication exchange; strong password rules do not by themselves make an exchange replay-resistant, but they reduce the value of a captured credential if one is intercepted.
