## Requirement

"Employ architectural designs, software development techniques, and systems engineering principles that promote effective information security within organizational systems."

## Objectives

[a] architectural designs that promote effective information security are identified;
[b] software development techniques that promote effective information security are identified;
[c] systems engineering principles that promote effective information security are identified;
[d] identified architectural designs that promote effective information security are employed;
[e] identified software development techniques that promote effective information security are employed; and
[f] identified systems engineering principles that promote effective information security are employed.

## Sufficient

- **A written reference to a published set of security design and engineering principles, with a statement of which ones apply to the environment.** A widely used source for this is the systems security engineering guidance in NIST SP 800-160, whose sections can be used to separate architectural design choices from systems engineering principles. [a][c]
- **A documented hardening baseline, such as a vendor-published or industry-published configuration benchmark, cited as the source of the organization's information security principles.** This can also support related configuration-management evidence elsewhere in the environment. [c]
- **A documented decision to purchase commercial off-the-shelf software rather than build custom applications**, stated explicitly as the organization's software development technique. This satisfies the software-development half of the requirement on its own but not the rest of it. [b][e]
- **For an organization running its systems primarily in a cloud platform, a written account of how the platform is accessed, why that access design was chosen, how endpoints connecting to it are hardened, and why those hardening choices were made.** This shows the architectural and engineering half of the requirement even where no custom development takes place. [a][c][d][f]
- **A reference to published secure coding practices** for any organization that does write custom software, cited alongside evidence that developers follow them. [b][e]

## Insufficient

- **A statement that the organization does not develop software, offered as the complete answer.** That statement only reaches the software-development objectives; the architectural-design and systems-engineering objectives still need their own identified principles and evidence of use. [a][c][d][f]
- **Treating this requirement as out of scope because there is no in-house development team.** Architectural design and systems engineering principles apply to any information technology footprint, developed in-house or not. [a][c]
- **Naming principles without showing they are actually applied.** The first three objectives ask what principles are identified; the second three ask whether those same principles are put into practice, and a list with no accompanying implementation evidence only reaches half the requirement. [d][e][f]

## Over-engineering

No documented position beyond the Assessment Guide; see confidence.

## Edge cases

- **Software that is itself the CUI deliverable, rather than software the organization uses to run its own information system.** This requirement is generally read as applying to the software and architecture of the organization's own information system, not to a software product built for a customer that happens to be the CUI in question; where that line is unclear, drawing a firm boundary between the delivered product and the internal system in the SSP resolves it.
- **A legacy environment designed before any structured security engineering effort existed.** The requirement does not demand retroactively redesigning everything; it expects the organization to identify applicable principles going forward and apply them to ongoing changes and upgrades, with any resulting gaps tracked as findings rather than treated as automatic non-compliance.
- **Whether a contract-required source code review satisfies the software-development half of the requirement.** Where a contract already mandates a source code analysis process, that process can generally serve as the evidence for the software-development objectives without a separate parallel process.

## Evidence examples

- **A document identifying the architectural designs in use**, such as network segmentation choices or a chosen cloud access model. [a]
- **A document identifying software development techniques**, including a commercial-software-only policy where applicable. [b]
- **A document identifying the systems engineering principles applied**, referencing a published source such as NIST SP 800-160. [c]
- **Implementation evidence tying each identified item to an actual configuration or practice**, such as a hardening baseline applied to endpoints or a secure coding checklist used during development. [d][e][f]
- **SSP language stating explicitly which principles were identified and confirming each is in use.**
