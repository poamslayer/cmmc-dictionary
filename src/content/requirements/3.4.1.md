## Requirement

"Establish and maintain baseline configurations and inventories of organizational systems (including hardware, software, firmware, and documentation) throughout the respective system development life cycles."

## Objectives

[a] a baseline configuration is established;
[b] the baseline configuration includes hardware, software, firmware, and documentation;
[c] the baseline configuration is maintained (reviewed and updated) throughout the system development life cycle;
[d] a system inventory is established;
[e] the system inventory includes hardware, software, firmware, and documentation; and
[f] the inventory is maintained (reviewed and updated) throughout the system development life cycle.

## Sufficient

- **A baseline document stating, at minimum, the major edition or version range approved for each asset type, the names of any organization-wide configuration items that apply (such as a companywide ports and services policy or a hardware standard), and every setting that is under configuration control.** Assessors have accepted this as the floor for content, regardless of format. [a][b]
- **Any of several implementation methods, provided the outcome is consistent: written build procedures, a standard image, or a set of policies that push configuration settings out.** Practitioner consensus treats the real test as whether assets of the same type end up configured the same way, not which mechanism produced that result. [a][c]
- **A smaller environment narrowing its own baselining burden by standardizing on fewer operating systems and fewer equipment brands, then tracking the result in a spreadsheet.** Assessors have accepted a spreadsheet as sufficient at that scale, where a more elaborate tool would be disproportionate. [a][d]
- **An inventory that names hardware, software, firmware, and documentation as four distinct line items, with a link to vendor documentation attached to each hardware or software entry.** Assessment Guide discussion calls out documentation and software as the two elements most often left out of an inventory that otherwise looks complete. [d][e]
- **A calendar-driven review cadence for the baseline (Assessment Guide example: a three-month reminder) tied to an update whenever a security risk or a software change is identified.** This satisfies the maintenance objectives without requiring continuous review. [c][f]

## Insufficient

- **A software inventory that lists what is installed but is not backed by any technical enforcement mechanism, such as a group policy or endpoint management platform capable of actually controlling what gets installed.** Practitioner consensus treats an inventory with no enforcement behind it as an incomplete baseline rather than a satisfied one, because nothing keeps the list accurate once written. [b][c]
- **A baseline that omits documentation links entirely, on the reasoning that hardware and software configuration is the only thing that matters.** The objective explicitly names documentation as a required element alongside hardware, software, and firmware; an inventory or baseline missing it does not meet [b] or [e].

## Over-engineering

- **A single all-encompassing baseline document that tries to capture every component of the entire environment in one artifact.** Because 3.4.2 also requires security configuration settings inside the baseline, one document covering everything grows unmanageable fast; a baseline organized per distinct component type satisfies the same objectives at far lower documentation cost. [a][b]
- **A separately documented configuration for every individual appliance instance, such as one write-up per physical printer.** Covering appliance types at a category level meets the same objectives; per-unit documentation for identical devices adds paperwork without adding assurance. [a][b]

## Edge cases

- **What counts as "the system" for baselining purposes.** One reading treats the entire corporate network or enclave as a single baseline target, which satisfies the hardware/software/firmware/documentation requirement in principle but creates a heavier maintenance burden than component-type baselines; the other reading breaks the environment into per-component-type baselines. Both appear in practice, and the outcome depends on the assessor. [a][b]
- **Whether every appliance needs its own documented configuration.** The practical view favors covering appliance types (all units of a given printer model, for example) under one baseline category rather than writing a distinct configuration per physical unit, but this is not a settled rule.

## Evidence examples

- **Baseline configuration document listing approved version ranges and every configuration-controlled setting.** [a][b][c]
- **Standard image build documentation** describing how a system is provisioned to match the baseline. [a][c]
- **Policy or endpoint-management exports** showing the settings pushed to devices of a given type. [b][c]
- **Inventory spreadsheet** listing hardware, software, firmware, and documentation references, sized to the organization. [d][e]
- **Vendor documentation links** attached to hardware or software inventory entries. [e]
- **Change or review log** showing when the baseline or inventory was last reviewed and what changed. [c][f]

## Related requirements

- **3.4.2** depends directly on this requirement: the security configuration settings it requires are established as part of the baseline this requirement creates.
- **3.4.3** and **3.4.4** govern how the baseline and inventory change over time once they exist; a baseline that never gets reviewed under those requirements will drift from what this requirement requires as "maintained."
- **3.4.6** and **3.4.7** depend on the inventory to know what hardware, software, ports, and services exist before anything can be restricted to essential capabilities.
