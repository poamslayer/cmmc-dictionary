## Requirement

"Provide audit record reduction and report generation to support on-demand analysis and reporting."

## Objectives

[a] an audit record reduction capability that supports on-demand analysis is provided; and
[b] a report generation capability that supports on-demand reporting is provided.

## Sufficient

- **A security-monitoring platform's analytics rules, with the ability to drill from a triggered rule down into the underlying raw logs, used as the reduction capability.** This pairing has been confirmed acceptable by a practitioner working as a third-party assessor. [a]
- **Almost any saved or ad hoc query counts as the reporting capability**, as long as the organization can demonstrate running it on demand. The bar is the ability to produce a report when asked, not a particular report format. [a]
- **A set of imported detection rules generating incidents from suspicious events, paired with dashboards summarizing the underlying data.** Dozens of rules across endpoints, cloud systems, and network devices, feeding a small set of summary views, has been described as a workable implementation. [a]
- **The specific queries, rules, and reports used are left to the organization to define**, rather than dictated by a reviewer; the objective only asks that on-demand analysis and reporting be possible, not that a particular tool or rule set be used. [a]
- **Where a security tool operates in a commercial, non-government cloud environment, treating it as a security protection asset and keeping CUI out of the log content itself**, logging events such as access, modification, deletion, and alerts as metadata rather than as the underlying protected content. [a]

## Insufficient

- **Relying only on summary dashboards without also using the platform's importable detection rules.** Dashboards alone leave significant reduction and correlation capability on the table that the same platform already offers; a reviewer who understands the platform may expect to see it used.

## Over-engineering

No documented position beyond the Assessment Guide; see confidence.

## Edge cases

- **Whether CUI content itself can end up inside log data.** The accepted position is that logs, by their nature, consist of metadata: who did what, when, from where, and with what outcome, and should not contain the underlying protected content. Where an event needs to reference something sensitive, referencing it by descriptive metadata, such as a filename or a general description of what was involved, rather than reproducing the content itself, is the safer pattern.
- **Whether a monitoring tool that touches a CUI-processing asset automatically becomes something that needs to be treated at the same handling level as CUI itself.** One position holds that where the organization has put reasonable safeguards in place so the log content stays free of protected information, this is not an issue. A stricter position, described as more widely held among reviewers generally, treats anything connected to a CUI asset as carrying enough risk of exposure to warrant caution regardless. The outcome depends on the assessor, and it is worth understanding a prospective assessor's leaning on this point before an engagement begins.
- **Splitting a dedicated, more restrictive CUI-handling platform from a broader commercial monitoring platform used for general internal log reporting.** This split arrangement has been discussed as workable, provided the commercial platform genuinely does not receive CUI content, with steps such as disabling automatic syncing between the two kept in place to prevent CUI from crossing over.

## Evidence examples

- **Screenshots or exports of analytics or detection rule configuration.** [a]
- **Summary dashboard or workbook reports built from the same data connectors as the detection rules.** [a]
- **A demonstration of running a query on demand and producing a report from it.** [a]
- **A list of configured data sources feeding the platform**, such as firewall, server, endpoint, and cloud activity logs. [a]
- **Unified audit log exports from a security and compliance console.** [a]

## Related requirements
